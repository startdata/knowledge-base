# 패널제어 의심 탐지 — 시나리오 설계부터 투표 합류까지 (2026-07-24 ~ 08-03)

## 문제·배경
- 이상온도의 원인 중 "사용자가 서비스(앱) 밖에서 물리 패널로 냉난방기를 조작"한 케이스를 선별하고 싶다.
- 제약: 스마트싱크 동기화가 **일방향(앱→현장)** — 시스템은 실제 기기 상태를 못 읽는다. `slaveDevice.power`는 서비스가 기억하는 상태일 뿐.
- 기존 A트랙 탐지(1h 평균 vs 설정온도)는 **가동 중(power=1) 컨트롤러 필수 조인**이라 꺼짐 공간이 사각.

## 핵심 설계 결정 (docs/panel-control-detection.md)
- 패널 사용의 조작적 정의: **"꺼짐(서비스 기준) + 서비스 제어이력 부재 + 능동적 온도 변화"** 의 결합. 직접 관측 불가하므로 물리적 배제("꺼진 기기는 온도를 능동적으로 못 움직인다")로 특정.
- 계절/mode 대신 **"외기 보정 후 방향 불문 변화"** — 간절기(냉난방 혼합)·꺼진 컨트롤러의 mode는 마지막 사용 모드라는 함정 회피.
- 제어이력 교차는 **isActivated(허브 전달) 기준** (isAction은 응답 유실 시 오인) — "놓치더라도 오인하지 않는다".
- "꺼진 지 오래됨"은 제외 조건이 아니라 **가중 조건** (수렴 상태의 급변 = 강한 신호). 막 꺼진 직후 잔여 관성은 −60분 이력 배제가 겸한다.
- 켜짐+반대방향은 이 노드가 판정하지 않음 — 원인 5종(패널 끔/고장/용량/제어누락/센서) 구분 불가 → 별도 노드 몫(이후 noresp가 담당).

## 실측 (dev leaf DB, MySQL 8.4.8)
- slaveLog 적재 주기 **~2.5분/행** (센서·컨트롤러 공통), `createdAt` 단독 인덱스 존재(EXPLAIN range).
- 무풍(냉방 안 도는) 상태 |Δ30분| **≤ 0.4°C** — 임계 2.5°C 대비 노이즈 바닥 충분히 낮음.
- 공간 내 설정온도 불일치 268/1025 공간 → 공간 평균 판정 흔들림 → **센서 단위 판정 + 과반 확정** 채택.
- 로컬 .env는 dev DB(센서 23대)였음 — Δ 분포의 prod 실측은 미완(임계 보정 잔여).

## 시행착오·교훈
- **efficiency 노드 하이브리드 개편을 만들었다가 전면 롤백** — 다른 팀원 담당 파일이었다. 교훈: 좋은 개선이라도 소유권 밖 코드는 수정 대신 설계 제안(문서)으로. 소거 순서표는 §10에 제안으로 남겼고, 이후 팀이 noresp 노드·스냅샷 전환으로 그 방향을 자체 구현했다.
- MySQL `SUM()` Decimal·`system` 예약어 크래시 → [[MySQL-Python 실무 함정]].
- 원인불명 케이스를 버리지 않는 **케이스 저널**(panel_journal, 90일)을 만들어 시나리오 밖 패턴 마이닝(LLM은 가설 생성기, 코드는 판정기)의 데이터 기반 마련.
