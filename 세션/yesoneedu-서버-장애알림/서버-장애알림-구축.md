## 문제 · 배경
- 운영: EC2 `t2.micro` 1대(Ubuntu, nginx → PM2 fork 1개, 앱 이름 `playground`), RDS PostgreSQL `db.t4g.micro`(20 GiB, `max_connections` 79, 비공개), 클라이언트는 Vercel.
- 헬스체크 엔드포인트 `GET /v1/status`는 있었지만 **호출하는 모니터가 없었고**, 앱만 살아 있으면 항상 `ok`라 **DB 장애를 못 잡았다.** 장애는 사용자가 알려줘야 알 수 있는 상태.
- EC2 루트 디스크 6.8 GB 중 73% 사용. 요청 로그·예외 로그·PM2 로그 모두 삭제 장치 없음.
- 두 번째 GitHub 계정(yesoneedu)으로 레포를 받는 것부터 시작 → 기존 계정과 SSH 키가 섞이는 문제를 먼저 해결.

## 접근 · 시행착오 (의사결정 서사)

### 1. 무엇으로 감시할까
- 처음 받은 제안: PM2 상태를 cron으로 CloudWatch 커스텀 지표에 보내기(A). 검토해 보니 PATH·실행 사용자·IAM 문제로 **거짓 알람 위험**이 크고, A만 잡고 외부 HTTP 체크(B)가 못 잡는 장애가 사실상 없었다 → **B를 기본으로, A는 보류.**
- 알람 기반 자동 재시작도 보류: PM2가 이미 크래시는 재시작하므로 알람이 울린다는 건 재시작으로 안 풀리는 상황일 가능성이 높고, 원인을 덮는다. → 사람이 누르는 **Slack 버튼 재시작**을 나중 단계(STEP 12)로.
- 모니터 수단: UptimeRobot을 추천했다가 사용자가 "AWS 안에서 관리"를 원해 재검토. **서울이 가능한지 공식 문서로 확인** → 검사 지역 유효값에 서울 없음, 지표·경보·SNS는 us-east-1 고정. EventBridge+Lambda(전부 서울)와 비교 후 **Route 53 상태 검사**로 확정: 코드 없음 + 서울 밖에서 검사해 서울 리전 장애도 감지. 알람이 버지니아에 있다는 건 콘솔 불편일 뿐.
- 처음에 "3개 지역이면 분당 6회"라고 설명했다가 문서를 읽고 정정: 간격은 검사 서버 하나 기준이라 실제로는 **분당 수십 회**.

### 2. 인프라 구축 순서
- Route 53 경보를 연결하려면 SNS·Chatbot이 먼저 필요해서 순서를 바꿈: SNS 2개(us-east-1, 서울) + Chatbot → Slack `#yestest-alert` → Route 53 상태 검사 → CloudWatch 경보 → RDS·EC2 경보 → EventBridge.
- 새 Route 53 콘솔은 생성 화면에 알림 설정이 없음 → CloudWatch(us-east-1)에서 경보를 직접 만들고, **OK 상태 알림도 추가**해 복구 알림을 받게 함.
- **HTTP(80)로 검사하면 nginx 301 리다이렉트 때문에 항상 정상**이 되는 함정 → HTTPS로. 추가 요금($1/월)이 여기서 생긴다.
- RDS 이벤트: 이벤트 구독을 SNS에 바로 붙이면 Chatbot 표시가 불확실해서 **EventBridge 규칙**으로.
- EC2 복구 경보를 만들다 **PM2 부팅 자동 시작이 없다**(`pm2-ubuntu` not-found)는 걸 발견 → 복구(=재부팅) 후 앱이 안 뜰 상태였다. `pm2 startup` + `pm2 save`로 해결.
- ALB 추가 검토: 서버 1대에서는 비용만 늘고 가용성은 같음 → 보류, nginx 유지.

### 3. 코드 계획 (아직 구현 전)
- 새 `/health` 대신 **기존 `/v1/status` 확장**(README에 헬스체크로 명시돼 있었음). DB 확인은 기존 `sequelize.authenticate()` + 3초 타임아웃, 실패 시 예외 대신 **503만 반환**(예외 필터 → 로그·Slack 폭주 회피).
- 문서 리뷰(doc-reviewer) MAJOR: "passthrough로 바꾼 503이 실제 응답에 남는가"가 가정이었다. Nest `master` 소스로는 덮어쓸 여지가 보였지만, **lock 버전 11.0.12로 실제 앱을 띄워 503 유지를 확인** → 대신 supertest 통합 테스트로 회귀 방지.
- 5xx Slack 알림: 모든 API, prod만, 5분 쿨다운, Map 100개 상한, 쿼리스트링·본문·IP 제외.
- 기준선 측정에서 **lint 기존 에러 1,298건**, 그리고 `npm run lint`에 `--fix`가 붙어 있어 실행하면 레포 약 1,000곳을 자동 수정한다는 것을 발견 → 완료 기준을 "변경 파일만, 새 에러 없음"으로 바꾸고 `npm run lint` 실행 금지.
- 커넥션 풀: 설정이 없어 Sequelize 기본 max 5, acquire 60초. DB 장애 때 Route 53 호출마다 60초 대기가 쌓인다 → **acquire 10초(X3)** 추가 결정. max는 `(코어×2)+1 ≈ 5`라 유지.
- 풀 고갈 위험을 찾으려 코드 분석: 음성은 S3·CloudFront 서명 URL로 직접 전달, AI 채점 호출은 트랜잭션 밖 → 문제없음. 대신 **결제 승인·취소 트랜잭션 4곳이 INICIS HTTP 호출을 트랜잭션 안에서 하고, axios 타임아웃이 없음**(X6) → 결제사 지연 시 전체 API 정지 가능. 결제 로직이라 별도 작업으로 분리 추천.

## 검증
- Chatbot "테스트 메시지 보내기" → 두 토픽(us-east-1, 서울) 모두 Slack 수신
- Route 53 상태 검사 Healthy 확인, `aws cloudwatch set-alarm-state ... ALARM`으로 강제 전환 → ALARM·OK 알림 모두 수신 (실서버 무영향)
- EventBridge 샌드박스에서 RDS 샘플 이벤트 패턴 일치. **실제 이벤트 수신은 아직 미확인**
- NestJS passthrough 503: 11.0.12 + 실제 `ResponseInterceptor` + URI 버저닝으로 임시 앱 실행 → `HTTP 503`, 본문 `statusCode: 503`
- Sequelize 풀 기본값: 설치된 6.37.7 `connection-manager.js`에서 `_.defaults` 병합 확인
- 헬스체크 HTTPS 조건: `curl --tls-max 1.2`로 TLS 1.2 응답 확인, HTTP는 301 확인

## 그 외 시행착오
- GitHub 두 번째 계정 SSH 별칭을 추가하자 **기존 github.com도 새 계정으로 인증**됨 → 기존 블록에 `IdentitiesOnly yes` 추가로 해결.
- RDS 로컬 접속: 엔드포인트가 맞아도 비공개라 직접은 불가 → TablePlus Over SSH(EC2 경유). EC2 사용자 이름은 Ubuntu AMI의 `ubuntu`, host key 지문은 `ssh-keyscan`으로 대조.
- Slack 앱 manifest: `incoming-webhook` bot scope에는 `features.bot_user` 필수. Webhook 테스트의 `no_service`는 URL 복사 문제.
- 운영 SSH 명령을 Claude가 실행하려다 자동 권한 분류기에 차단됨(`.env.prod` 조회까지 묶은 게 범위 초과) → 사용자가 직접 실행.
