## 문제 · 배경
- B2B 매장 IoT 구독 서비스(NestJS 9, MySQL 8, Redis, pm2 단일 인스턴스, Kafka 인프라 보유). 기존 결제는 아임포트(포트원 v1) **PG 측 예약결제**에 위탁, 웹훅 수신 없음, 재시도·환불·대사 없음.
- 요구: 모든 결제방식(정기·단건·CMS·이체·무통장·복합) + 할인·쿠폰·환불·포인트·캐시를 **설계는 최대로**, 구현은 단계별로(각 단계 자체 동작). 상품구성·결제요청·결제·정산 모듈은 **각각 다른 서비스**로 취급(정산은 어드민 서버로 갈 수 있음, 배치 미정). 결제 실행은 PG·CMS 위탁. 대기업 보편 아키텍처 반영. 베트남 확장 가능성.
- 사용자가 가져온 초안(`critical-points.md`)은 정산·원장 관점이 강했고, 결제 계층의 입력 계약과 결제수단별 차이가 비어 있었다.

## 접근 · 시행착오 (의사결정 서사)

### 1. 조사 → 평가 축을 바꾸다
- 국내(토스·카카오페이·네이버페이·배민·포트원) / 해외(Stripe·Adyen·Uber·Airbnb·Square·Braintree·Modern Treasury) / 구독 청구 모델(Stripe Billing·Chargebee·Recurly·Zuora·Lago·Kill Bill) / 원장·멱등성 패턴 4축으로 병렬 조사.
- 첫 평가 문서는 "현재 인프라에서 가능한가"로 썼다가 사용자가 **"요구사항에 맞는 것을 찾아달라"**고 정정 → 요구사항 R1~R17을 먼저 목록화하고 사례를 대고 다시 평가. 결론은 **Kill Bill의 경계 + Stripe의 객체 모델 + 토스페이먼츠의 데이터 구조·신뢰성 규칙 합성**. 한 사례가 전부를 덮지 않으며, 층마다 출처 하나·같은 질문에 답 하나 원칙.

### 2. 뒤집힌 판단들
| 처음 | 정정 | 계기 |
|---|---|---|
| 청구서는 상품구성이 발행(초안 1.8) | **결제요청 모듈이 발행**, 상품구성은 계산기(`PriceQuote`) | 상품 구성은 언제든 바뀌므로 스냅샷을 굳히는 모듈이 소유해야 함 |
| 포인트·캐시는 이번 범위 제외 제안 | **설계에 전부 포함**, 구현 6~7단계 | "모든 것이 고려된 시스템" 요구 |
| 결제 계층 단일 상태 컬럼·수단 1개 | 결제→분담(tender)→시도(attempt) 3층, 1단계도 분담 구조 유지 | 복합결제·제휴쿠폰을 나중에 넣을 때 전 쿼리 수정 방지 |
| 전달은 인프로세스 디스패처, Kafka는 분리 시 | **Kafka 처음부터** → 다시 **결제 모듈 안팎만 Kafka**, 나머지 outbox+인프로세스, 토픽별 설정 | 사용자: 인프라 보유 → 이어서 "단일로 할 수 있는 건 단일로, PG 호출 부분만 Kafka" |
| "커밋 직후 인프로세스 알림으로 즉시 기동" | 워커 프로세스 분리 + 1~2초 폴링 | 리뷰: 워커가 별도 프로세스면 인프로세스 알림이 도달하지 않음 |
| 환불 1단계 포함 | **운영 취소(전액)만 1단계**, 고객 환불은 정책 확정 후 | 환불 정책 미정. 그러나 잘못된 결제는 되돌려야 함 → 취소/환불 분리 |
| 세금계산서는 결제 확정 후 발행 | 공급시기 기준, 세무 확인 항목으로 격하 | 리뷰: 법 단정 |
| 원문 보존 5년(전자상거래법) | 법무 확인 전 삭제 배치 없음 | 리뷰: B2B 적용 여부·타 법 보존 의무 미확인 |
| 상품구성이 부가세까지 계산 | 상품구성은 공급가액·할인, **결제요청이 세금 규칙 적용** | 세율은 상품이 아니라 청구 법인·고객에 달림(해외 확장) |
| 수수료를 청구서에 기록 | 청구서에는 없음, **정산 모듈이 예상·실제 분리 저장** | 수수료는 정산의 사실 |
| 자사포인트·제휴포인트 구분 | 포인트는 자사 적립 한 종류 | 사용자 정정 |

### 3. 독립 리뷰가 잡은 설계 결함 (→ [[세션/leaf-결제개편/리뷰-반영]])
타임아웃 복구 "조회→없음→FAILED→새 키 재시도"의 이중 승인, 고아 HOLD 1시간 해제가 지연 확정 수단의 정상 HOLD를 풀음, 재시도와 중복 이벤트 구분 규칙 부재, 대표 실행 그림이 모듈 소유권 원칙 위반, 운영 취소 검증 주체 오류 등.

### 4. 사용자 질문으로 정리된 개념
- "outbox는 DB와 기능이 한 서버에서 해결 안 될 때 쓰는 것 아닌가?" → 맞다. 한 DB에서는 정합성 장치가 아니라 **경계·장애 격리·전달 교체용**. "outbox 구현에 Kafka가 필요한가?" → 아니다, 릴레이 목적지는 무엇이든. "결제 실패가 청구서를 취소하면 안 되니까" → 그것이 모듈을 나눈 이유.
- "재시도는 첫 시도의 키와 같아야 하지 않나?" → 타임아웃 재전송은 같은 키, 거절 후 재시도는 새 키(같은 키면 거절이 재생돼 영원히 실패). 키 `{결제ID}-{시도번호}`로 첫 시도를 드러냄.
- "7월 청구서가 8월에 결제되면 어느 달에 보이나?" → 날짜 3종. 고객은 청구 기간, 정산은 확정일.
- "승인 상태가 왜 있나?" → 국내 카드는 없음. 월렛 선점·해외 PG용. 이름을 `HELD`로.
- "0원 결제(3개월 무료)도 되나?" → TRIALING 없이 100% 할인 0원 청구서 매달 발행.

## 결정 (33건 중 핵심)
- 모듈: 상품구성(catalog) → 결제요청(billing: 청구주체·구독·청구서·세금라인·이용권·재결제) → 결제(payment: 수단·결제·분담·시도·취소) → 정산 / 월렛 / 알림. 각각 테이블 소유권·계약 DTO·outbox/inbox·포트로만 통신.
- 1단계 = 모놀리스(논리 분리) + 워커 프로세스 + 결제 경계만 Kafka(토픽 2개, 컨슈머 그룹 4개). 이후 토픽별 설정으로 전체 Kafka 전환.
- 단계: 정기결제 → 단건 → CMS → 자동이체(의미 확인) → 무통장 → 복합결제(포인트) → 제휴쿠폰·캐시.
- 즉시 결제: 등록 시 청구서 발행 + 결제 요청 outbox 한 트랜잭션, 릴레이 1~2초.
- 취소(운영, 1단계) vs 환불(정책, 미정). 재시도 정책 미정 → 1단계 자동 0회 + 관리자 수동.
- 해외 확장 선반영: currency, billing_entity, tax_rule(1행 10%), 증빙 포트, provider 국가, UTC.
- 미결(리서치·구현에서): 청구 주체 단위, 이용권 소속, 단건 결제 성격, 행위자 기록 형태(서비스 계정 vs 어드민), 4단계 자동이체 의미, 청구 기준일, PG 선정, CMS 기관·수수료 방식, 세무·법무 항목.
