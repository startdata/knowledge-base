# 결제 개편 설계 문서 리뷰 — 잡힌 결함과 반영 (2026-09-15)

> 세션: [[세션/leaf-결제개편/설계결정-서사]] · 개념: [[결제 상태 기계]] [[멱등성]] [[복합결제 전부-또는-전무]] [[모듈러 모놀리스]] [[웹훅 처리 패턴]]

설계 문서와 평가 문서를 각각 독립 리뷰어(doc-reviewer)에게 맡겨 나온 지적을 분류하고, 무엇을 받고 무엇을 기각했는지 기록한다. 같은 실수를 반복하지 않기 위한 목록.

## 설계 결함 (전부 반영)
| 결함 | 시나리오 | 수정 |
|---|---|---|
| 타임아웃 복구가 이중 승인 | attempt#1 타임아웃 → 조회 "없음"(PG 지연 처리 중) → FAILED → attempt#2 새 키 → 둘 다 승인 | 재전송(같은 키) vs 재시도(새 키) 분리. 타임아웃은 재전송만. PG 문서상 확정 시간 전 FAILED 금지 |
| 고아 HOLD 1시간 해제 | 포인트 + 가상계좌(D−7) → 1시간 뒤 HOLD 해제 → 3일 뒤 입금, 확정할 HOLD 없음 | 형제 분담 종단 기준 판정, 만료는 수단 리드타임 기준 |
| 재시도 vs 중복 구분 없음 | 청구서 ID 유니크 위반 시 무시할지 시도 추가할지 불명 | 결제 upsert + `(payment_id, attempt_no)` 유니크 |
| FAILED 종단인데 같은 결제 재시도 | 상태 재진입·수단 교체 시 분담 재구성 규칙 없음 | 결제 OPEN 상태, 분담 SUPERSEDED |
| 보상 취소 실패 표현 불가 | 카드 확정 + 쿠폰 실패 → 취소 실패 → 결제 FAILED인데 카드는 승인 | COMPENSATING 상태 |
| 부분 환불·취소·재청구 동시성 | SELECT SUM 후 INSERT 경합, 동시 취소 클릭, VOID 후 재청구 유니크 위반 | refunded_amount 조건부 UPDATE, `(payment_id, kind, active_key)` 유니크, 청구서 유니크에 active_key |
| 웹훅 이벤트 ID 없는 PG | event_id 유니크만 가정 | `(결제키, 상태, 시각)` 해시 대체 키 |

## 원칙 위반·모순 (전부 반영)
- 대표 실행 그림(5.4)이 결제요청 트랜잭션에서 결제 모듈 테이블에 쓰는 것으로 그려짐 → 5.11 구조로 재작성.
- 운영 취소에서 결제요청 모듈이 환불 행 생성 + PG 취소 기간 검증 → 검증·생성은 결제 모듈, 결제요청은 요청 이벤트만.
- 이용권 소속이 네 곳에서 다름 → 1단계 결제요청 내부, 자기 테이블·포트(확인 필요 표기).
- 명령용 outbox가 이벤트 outbox 위에 또 있음 → inbox 행이 곧 명령. 트랜잭션 4개 → 3개.
- 금액 개념이 제휴쿠폰 시 둘로 갈림 → taxable/total/payable 3종 고정.
- 환불 결과가 두 이벤트 → RefundResult 하나.
- 평가 문서 "워커 전용 프로세스"와 설계 "커밋 직후 인프로세스 알림"이 동시 성립 불가 → 폴링 1~2초.

## 근거 없는 단정 → 확인 필요로 격하
세금계산서 발행 시점(공급시기 기준), 카드=매출전표/CMS=세금계산서 이분법, 전자상거래법 5년 보존, CMS D+1(입금 기한을 출금 결과 시점으로 오독), Adyen 64자·UUID v4, Stripe "결제 1시간 전 확정", 평가 문서의 Kill Bill 수동 재시도 API·Stripe BalanceTransaction·billing_cycle_anchor·카카오페이 outbox 귀속·"해외 대형사는 브로커 없이" 일반화.

## 기술 서술 정정 (평가 문서)
SQS FIFO 제한은 규모상 무의미(Standard + inbox), DynamoDB 부적합 이유는 유니크 제약이 아니라 조인·조회(Uber는 결제에 사용), 스키마 분리만으로 트랜잭션을 못 막음(DataSource·DB 계정이 막음), Kafka 재생은 retention 한계·원천은 DB.

## 기각한 지적 (이유 기록)
- "1단계에 미사용 테이블 전부 생성은 과잉" → 요구사항이 최대 설계. 단, 세무·법무 미정 항목은 두 표현 가능한 형태로만 두고 굳히지 않는다는 문장 보강.
- "결론(모놀리스 → 분리 이행)을 바꿔라"는 지적은 없었음. 근거·비용 서술을 정직하게 고치면 유지 가능 판정.

## 교훈
- 문서를 여러 번 덧대면 절마다 다른 시점의 결정이 남아 모순이 생긴다. 결정이 바뀌면 관련 절을 한 번에 다시 쓰는 편이 낫다.
- "명시", "있음" 같은 단어는 조사 자료에서 확인한 것에만 쓴다. 근거 등급(조사/외부/비공식)을 표기하면 나중에 검증 대상이 자동으로 드러난다.
- 실행 그림 하나가 원칙 문장 열 개보다 강하다. plan 작성자는 그림을 따른다.
