> 개념: [[Kinesis 컨슈머]] §6 · [[재시도 전략]] · [[Spring DataAccessException 계층]] · [[Java 스레드 인터럽트]] · [[Poison message]] §6 · [[멱등성]] · [[Testcontainers]] · [[Outbox 패턴]]
> 앞선 기록: [[세션/씨드앤-액션이력-파이프라인/설계결정]] (파이프라인 전체 설계). 이 문서는 그중 **컨슈머 실패 처리**가 구현 단계에서 어떻게 바뀌었나.
> 리포: `sdn-kinesis-consumer` 브랜치 `BE-570`, 커밋 `95a596b`. 지라 BE-570(에픽 BE-546).

## 문제 · 배경
- 설계 문서(02)는 "일시 실패는 상한 없이 재시도, 영구 실패만 `failed_events` 격리"였다. 실제 컨슈머는 직접 폴링 대신 **기존 `sdn-kinesis-consumer`(Spring Boot 3.5 + KCL 3.0.1, Java 21) 재사용**으로 결정돼(2026-09-16) 2026-09-15에 `action-history-dev` 프로필로 배포된 상태. 격리 저장소는 `failed_events` 테이블 대신 **S3 DLQ**(기존 컨슈머의 방식).
- 리서치(`research.md`)에서 배포분의 RDS 경로를 읽어 보니: `TransientDataAccessException`만 **5회** 재시도(워스트 약 3.1초) 후 DLQ. 연결 실패(`CannotGetJdbcConnectionException`)는 Spring 계층상 NonTransient라 **재시도 0회로 즉시 격리**. DB/haproxy가 3초 끊기면 그동안의 정상 레코드가 전부 S3로 빠지고 체크포인트는 넘어간다. 재적재 도구는 없다.
- 그리고 이 프로젝트 전체의 fail-closed 설계 — `DeadLetterSink`가 S3 실패 5회 뒤 예외를 던져 "체크포인트를 막는다", `DynamoBatchWriter`의 "propagate so KCL re-delivers" — 가 하나의 전제 위에 있었다: **KCL이 예외를 받으면 배치를 다시 준다.**
- 제약: 공유 클래스라 caps 컨슈머 2개(caps-dev/prod, DynamoDB+RDS)에도 같이 배포된다. Jenkins는 `develop` 브랜치만 빌드·배포하므로 develop 머지 = 두 컨슈머 동시 배포.

## 접근 · 시행착오

### 1. 계획 v1 → v2: "사유 분리 후 DLQ"에서 "차단 재시도"로
- v1은 소진 시 `RDS_WRITE_RETRY_EXHAUSTED` 사유를 따로 만들어 DLQ에 보내고 대사가 재발송하는 안. 사용자 지시: **"연결 실패는 DLQ가 아니라 재연결 후 Kinesis에서 다시 가져와야 한다."**
- "다시 가져오기"를 어떻게 하나 → KCL 3.0.1 `ProcessTask.callProcessRecords` 소스 확인: **예외를 삼키고 `Skipping over the following data records` 로그 후 넘어간다. 재전달 없음.** AWS 가이드 동일. 즉 이 리포의 fail-closed는 전부 유실 경로였고(S3 장애 시 같은 배치의 정상 레코드까지 사라짐, caps 포함), 2026-09-14 prod에서 DynamoDB 스로틀 예외가 KCL까지 새서 1,246건이 유실된 사고가 같은 원인이었다.
- 선택지: 처리 스레드 안 **차단 재시도** vs `Runtime.halt(1)` 재시작. halt는 같은 프로세스의 다른 스트림 워커(매핑별 격리 원칙)까지 죽여 제외. 총 시간 상한(1시간 후 DLQ)도 검토 — 긴 장애에서 정상 레코드가 격리되므로 제외, **알람이 상한 역할**.
- 결과 A: `RdsUpsertWriter.isRetryable` = Transient + `DataAccessResourceFailureException`, 상한 없음. `retry.max-retries`는 백오프 램프 고정 시점으로 의미 변경(설정값은 그대로). `consumer.rds.retry` 카운터 신설 — 차단 중엔 IteratorAge 데이터포인트가 사라지고 앱 gauge는 마지막 값에 머무니 카운터가 유일한 직접 신호.
- A'(사용자 확정): `DeadLetterSink` S3 쓰기도 차단 재시도. `dlq.write.failure`는 첫 실패 1회만(기존 알람 유효).

### 2. B·C·D — 대사·계약·검증
- B: DLQ JSON에 `itemKey`/`itemSortKey`(매핑의 partition/sort-key-attr 값). 처음엔 action-history 전용 `eventId` 필드 안 → **컨슈머별 분기 없이 매핑 설정 값을 일반화**. S3 키 구조 변경은 caps DLQ 키도 바꾸므로 사용자가 거부. 일시 실패가 DLQ에 안 오게 되면서 대사 E의 규칙이 "S3 `dlq/`에 있으면 제외" 한 줄로 단순화.
- C: 갱신 컬럼 allowlist `rds-update-columns`. 배포분은 PK 제외 전 컬럼을 `VALUES()`로 갱신 — pin 컬럼이 item에 없어 우연히 보호되는 상태였다(00 3.5 계약 "메타 3컬럼만" 위반). 미설정(caps)은 기존 동작. 빈 갱신 절은 `eventId = eventId` no-op — 절 생략은 중복 키를 `DuplicateKeyException`(영구)으로 만드는 잠재 버그였다. `INSERT IGNORE`는 금지(02 🔴).
- D: `ActionHistoryRdsIT` — MySQL 8.4 Testcontainers, **handoff 문서의 `action_history.sql`을 직접 실행**(복사본 = 드리프트). 시나리오 7개: ① 적재·메타 주입 ② 재전달 멱등+메타 갱신 ③ 어드민 pin 보존 ④ STRICT 잘림 → 그 건만 DLQ(itemKey=eventId), 다음 건 저장 ⑤ 배치 내 dedup ⑥ allowlist로 본문 불변 ⑦ **`docker pause` 3초 → 차단 → unpause → 저장, DLQ 0, 체크포인트 1, 재시도 지표 ≥ 1**.

### 3. TDD 진행과 환경 시행착오

### 4. 리뷰(reviewer 에이전트)가 잡은 것 — 계획의 전제 오류 2건
- **BLOCKER**: IT가 읽는 DDL이 미추적 폴더(`docs/action-history-consumer/`) → Docker 있는 Jenkins에서 `FileNotFoundException`으로 7건 전부 실패 → 빌드 차단. 사용자 결정: 폴더를 커밋에 포함(09-16부터 열려 있던 gitignore 결정 종결).
- **MAJOR 1 — 계층 전제 오류**: 계획·문서가 "server has gone away ⊂ `DataAccessResourceFailureException`"으로 적었지만, Connector/J `CommunicationsException extends SQLRecoverableException` → Spring `RecoverableDataAccessException`(Transient도 ResourceFailure도 아님). **실행 중 절단은 영구로 분류돼 격리**되던 것. 리뷰어가 `~/.gradle/caches` jar를 `javap`로 열어 확인. 계획이 Spring javadoc URL을 인용했음에도 드라이버 쪽은 추정이었다 → 교훈: **두 라이브러리 경계를 넘는 매핑은 양쪽 소스를 다 본다.** 단위 테스트는 내가 고른 예외를 던지므로 못 잡는다.
- **MAJOR 2 — 인터럽트 오분류**: 계획은 "인터럽트면 `awaitBackoff`가 던져 루프 밖으로 전파, shutdown 중이니 그대로 둔다"였는데, 전파 지점 바로 위 RDS 루프의 `catch (Exception e)`가 그것을 잡아 `RDS_WRITE_FAILURE`로 DLQ에 보냈다. 플래그가 복원된 상태라 다음 유닛의 `awaitBackoff`도 즉시 던져 **배치 나머지 전부 DLQ → 체크포인트**. 수정: 플래그 확인 분기로 DLQ·체크포인트 없이 `return`.
- MAJOR 4·5: caps 실제 경로(`updateColumns == null`) 테스트 부재, `rds-upsert-keys` 생략 시 NPE(fail-fast 메시지가 가장 흔한 오설정에서 안 나옴). MINOR 8건(로그 스로틀 주석 "≈1분"은 caps-prod max-backoff 20s면 ~10분, IT `socketTimeout` 플래키 가능성 등)은 미반영.
- 리뷰어는 IT를 실행 없이 코드로 검토해 ④(1406/22001 → SQLState 폴백 → `DataIntegrityViolationException`)·⑦(`DataSourceUtils.getConnection`이 모든 SQLException을 `CannotGetJdbcConnectionException`으로 감쌈)의 성립을 jar 수준에서 먼저 확인했고, 이후 실제 실행으로 재확인됐다.
