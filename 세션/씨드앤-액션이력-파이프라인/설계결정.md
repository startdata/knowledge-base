# 사용자 행동·기기 상태 이력 파이프라인 — 설계 결정 (씨드앤, 2026-06 ~ 2026-09)

## 문제 · 배경
- 이력이 주요 기능 39종만 기록됐고, 자사·협업사 냉난방기 제어 서비스 2개와 통합 어드민이 **어드민 서버 API를 거쳐 어드민 DB**에 저장하는 구조. 첫 설계가 "어드민에서만 조회"를 전제로 빠르게 만들어져 부하·순서·원자성을 고려하지 않았다
- **어드민 서버가 단일 장애 지점.** 배포 중·장애 시 세 서비스의 이력이 동시에 유실됐다. 서비스 기능은 멀쩡해서 유실을 나중에야 알게 됨
- **dual write.** 기능 처리와 이력 기록이 별도 요청이라 "기능 실패 + 이력만 남음", "기능 성공 + 이력 없음" 양방향 불일치가 실제로 발생 (통계는 없음)
- 외부 설치 업체 도입 후 설치기사가 기기 데이터를 실수로 삭제하는 사고. 설치기사 작업은 이력 대상이 아니어서 CS팀이 서버 로그를 뒤져야 했다
- 기기 상태 이력(끊김·복구, 17종)은 별도 테이블이라 사용자 액션과 함께 볼 수 없었다
- 제약: 서비스 담당자가 각각 달라 **적용 코드 변경 최소화**, 데브옵스 최소화로 **인프라 추가 최소화**, 3개 서비스·5개 클라이언트(웹/앱) 공통, 베트남어·영어·한국어 지원, 계정별 조회 범위
- 규모: 리뉴얼 전 어드민 이력 API 일 호출 10.2k(조회+쓰기), 쓰기만 2.4k. 하루 이력 약 900~1,000건. **규모가 아니라 정합성·가용성 문제**였다는 점이 설계 판단의 출발

## 접근 · 시행착오 (의사결정 서사)

### 대안 검토
1. 서비스 DB마다 이력 테이블 + 같은 트랜잭션 저장 — 가장 단순하나 매장·브랜드 기준 통합 조회와 전사 통계 요구로 **중앙 집중이 필수** → 제외
2. 액세스 로그·Loki — 요청·응답 본문 없음, CS팀이 화면에서 검색·대응해야 해 사용성 부족 → 제외
3. 서비스가 Kinesis 직접 발행 — 커밋 전 발송은 유령 이력, 커밋 후 발송은 유실(fire-and-forget in-flight 유실 실측) → 제외
4. Outbox 릴레이를 CDC(Debezium Server / AWS DMS)로 — 상시 인스턴스·binlog·변환 계층·모니터링 추가. 이력은 초 단위 지연 허용이라 이점 없음 → 폴링 릴레이 선택
5. Kinesis vs Kafka — 데드락 프로젝트 때는 EventHub(Kafka 프로토콜), 이후 라이브러리 때 MSK·EventHub 혼용. **비용 절감으로 전사 Kinesis 이관**이 이미 된 상태라 Kinesis

### 스키마
- 행위자·서비스·클라이언트·액션·대상·시각을 공통 컬럼, 기능마다 다른 상세(변경 전·후 값 포함)는 JSON 컬럼. 대·중분류 카테고리
- `serviceId`는 "전송 주체"가 아니라 **`userId`의 네임스페이스** — 리프·파트너스가 서로 다른 유저 테이블이라 userId만으로는 다른 사람이 섞임. `clientId`(웹/앱)로 대체하는 안은 제외: 같은 사용자의 행동이 갈라지고 레코드가 자기 설명적이지 않음
- **required + nullable** 규칙: `storeId`·`userId`는 키 생략 시 throw, `null`은 명시적 부재 → 컨슈머가 "누락"과 "해당 없음"을 구분. 컨슈머에 `?? null` 분기 불필요
- 기기 상태 이력을 같은 테이블에 통합: 기존 조회 쿼리 5개를 대조해 `status→subCategory`, `eventTime→occurredAt`, 매장 범위→`storeId`로 전부 대응됨. 기기 속성은 memo JSON. 새 컬럼·새 eventType 불필요 → `userId` nullable 결정
- 고정 메시지는 저장하지 않고 카테고리별 템플릿을 코드로 관리해 3개 언어 렌더링. 수동 입력 이력·기기 속성만 저장. 저장된 사실은 불변
- 브랜드 단위로 남긴 이력이 소속 매장별 조회에도 보이도록 `groupId`로 연결
- `schemaVersion`·`eventType`·`seq`는 저장하지 않음 — 현재 상수라 정보량 0, 필요해지면 컬럼 추가 + DEFAULT 백필로 정확히 복원. 단 새 버전 발송 전 컬럼 추가 선행 절차 명문화
- FK 미설정 — 서비스별 유저 테이블이 다른 DB, 비동기 적재라 룩업보다 이벤트가 먼저 도착 가능. 이상값은 적재 후 집계 쿼리로 탐지
- `isPinned`/`lastPinnedAt`(어드민 고정 기능)은 envelope에 넣지 않음 — 이벤트(불변 사실)와 사후 상태(가변) 분리. 넣으면 재전달 시 no-op upsert를 깨고 pin을 덮어쓰는 코드를 유도
- 이력 PK = `eventId`(UUID v7, CHAR(36)). Outbox PK는 반대로 auto-increment + eventId UNIQUE — 매초 스캔되는 `(status, id)` 보조 인덱스 크기와 정확한 삽입 순서
- 저장소는 RDB(어드민 DB 공유). 별도 이력 서비스 안 만듦: 쓰기 주체 컨슈머 하나, 읽기 주체 어드민 하나라 캡슐화할 호출자가 없음. RDB 여유·팀 선호·DynamoDB 이관 경험으로 나중에 옮길 수 있음. 용량 월 증가량 추적해 NoSQL/S3 이관 시점 판단

### Outbox · 릴레이
- 서비스 트랜잭션 안에서 Outbox INSERT. **검증·이벤트 ID 발급을 기록 시점으로 이동** (처음엔 ID 발급이 라이브러리 발송 시점에 있었고 검증도 발송 시점 → 잘못된 payload가 커밋 후 영구 유실되는 구멍 발견 → `buildOutboxRow` 헬퍼로 이동). 현재 2중 검증(기록+발송)은 유지하기로 결정, 대신 스키마를 엄격하게 바꾸는 배포 전 pending drain 규칙
- 릴레이는 각 서비스 파드 안 1초 폴링. K8s 파드 2개 상시 + 오토스케일이라 **중복 발송 문제** 존재 → 멱등 upsert가 정합성은 지키므로 비용 문제로 격하 → tick 단위 `GET_LOCK` 리더 선출 구현 (검증 중)
- 발송 실패 **row 단위 격리**: 인코딩 불가 row만 `failed` 표시 + Slack 알림, 나머지 계속 발송. PutRecords 레코드별 ErrorCode 분리, 배치 500 제한
- complete 행 7일 보관 — 처음 근거는 "Kafka 기본 7일 참고"였으나 **Kinesis 보존 1일보다 긴 DB 장애 시 재발송 소스**로 재정의
- 파티션 키 `serviceId#u#userId` / `serviceId#d#deviceType-deviceId` (라이브러리 자동 생성). 처음엔 접두어 없이 `serviceId#userId`였는데 사용자·기기 ID가 둘 다 숫자라 충돌 가능 → 타입 접두어 추가. 샤드 1개
- fallback API(재시도 초과 시 어드민 API 호출)는 **만들지 않음** — Outbox가 있으면 Kinesis 장애는 지연일 뿐이고, fallback은 순서 역전·중복 경로만 늘림

### 컨슈머
- EC2 1대 + Java, KCL 없이 GetRecords 직접 구현. Java 선택 이유: 이전 Kafka 컨슈머(워커 8개)도 Java, 컨슈머는 JVM으로 두는 팀 기조 + 장기 실행 안정성. KCL 미사용: 샤드 1개·인스턴스 1개라 리스 분배 불필요, DynamoDB 의존 회피
- 순서 무관 설계: `occurredAt` 정렬 + `eventId` 멱등. 저장 시각(`createdAt`)은 DB 기준 별도
- 저장 성공 시에만 체크포인트. 체크포인트 저장 위치는 **별도 테이블 대신 `user_action_history`의 `shardId`·`kinesisSequenceNumber` 컬럼**(DECIMAL(65,0), MAX로 재개)으로 결정 — 저장 자체가 체크포인트, 테이블 추가 없음
- 실패 분류(일시/영구) + `failed_events` 격리는 구현 예정. 릴레이 실패는 Outbox status, 컨슈머 실패는 failed_events — 단계별 하나씩. 대사 DAG가 failed_events를 제외해야 영구 거부 이벤트 재발송 루프 방지
- 알림은 Slack만. 재처리 UI 없음(극소수)

### 보정
- Airflow DAG 2개: 대사(매일, complete인데 이력에 없는 eventId → pending 복원) / Outbox 정리(7일)
- 이관: 기존 테이블 유지 + 새 테이블 이중 쓰기 + 과거 데이터 변환 스크립트(1일 청크). createdAt 기준 UUID v7 생성. 이중 쓰기와 겹치는 구간은 createdAt·필수값 동일 시 스킵

## 남은 과제
- 컨슈머 실패 분류 + failed_events, 이터레이터 만료 재발급, 적응형 폴링(업무문서 D·Q)
- 관측 지표: 가장 오래된 pending 나이 알림(F), IteratorAge 대용 `MillisBehindLatest`
- 샤드 증설 기준: `WriteProvisionedThroughputExceeded`·IteratorAge 지속 증가·retryCount 증가. 레코드 247B라 1,000 rec/s 상한, DAU 10만×50건 = 샤드 1개 29%
- 라이브러리에 Outbox DDL·릴레이 모듈 포함(P)

## 오버엔지니어링 반론 정리
규모(하루 1만 건)로 방어하면 진다. 바꾼 이유 3개(SPOF 유실·dual write·39종 한정)는 전부 정합성·가용성·범위 문제라 하루 100건이어도 같다. 논리 사슬: 중앙 집중 요구 → 서비스 DB ≠ 어드민 DB → dual write → Outbox(가장 가벼운 해법) → Kinesis(이미 사내 버스, 인프라 0). 안 한 것 목록(샤드 1·CDC X·Registry X·별도 서비스 X·Error Topic 대신 DB·fallback X·schemaVersion 컬럼 X·FK X·RDB 유지·폴링·Lambda ESM 검토)이 절제의 증거. 간단한 버전(어드민 API)을 먼저 했고 운영에서 깨진 뒤 바꾼 두 번째 반복.
