# 구독 청구 도메인 모델 (Subscription Billing)

> [[결제 상태 기계]] · [[에누리와 청구할인]] · [[Kill Bill]] · [[Stripe PaymentIntent]] 와 연결.
> 세션: [[세션/leaf-결제개편/설계결정-서사]]

## 1. 표준 계층 (Stripe Billing · Chargebee · Recurly · Zuora · Kill Bill 공통)
```
Customer / Account          청구 주체. 결제수단 보유
 ├─ PaymentMethod           저장된 수단(빌링키·계좌)
 ├─ Subscription            무엇을 어떤 주기로
 │   └─ SubscriptionItem    상품·가격·수량
 ├─ Coupon / Discount       할인 규칙과 적용 결과
 └─ Invoice                 한 청구 주기의 청구서. 확정 후 불변
     ├─ InvoiceLine         라인(할인은 여기)
     ├─ CreditNote          사후 정정 문서
     └─ Payment → Attempt / Refund
```
- **정기와 단건은 결제수단이 아니라 청구 주기다.** 정기 = Subscription이 주기마다 Invoice를 만들고 저장 수단으로 결제. 단건 = Subscription 없는 Invoice 하나. 결제 계층에서 둘은 같은 Payment.
- **청구서는 확정(finalize) 후 불변.** 상품 가격이 바뀌어도 발행된 청구서는 그대로. 정정은 CreditNote(Zuora는 CreditMemo/DebitMemo). 결제 모듈이 상품 테이블을 실시간 조회하면 이 원칙이 깨진 것.
- **계산은 한 곳에서만.** 상품구성(계산기)이 `PriceQuote`를 돌려주고 청구 모듈이 스냅샷으로 굳힌다. 결제 신청이 `총액 − 쿠폰`을 직접 계산하면 할인 로직이 두 곳에 생긴다.

## 2. 상태
- Invoice: DRAFT → OPEN(확정) → PAID / VOID / UNCOLLECTIBLE. 결제하는 날 만들면 DRAFT가 필요 없다(Stripe는 draft 생성 후 짧은 유예 뒤 자동 확정·결제 시도).
- Subscription: ACTIVE / NON_RENEWING / CANCELED / PAUSED. **미납 상태는 여기 두지 않는다.**

## 3. 청구(Billing)와 이용권(Entitlement)의 분리 — Kill Bill
"돈이 들어왔나"와 "쓸 수 있나"는 다른 질문. 미납 후 며칠 유예할지는 결제 사실이 아니라 정책이고, 정책은 서비스 쪽(이용권)이 갖는다. Stripe는 `past_due`를 구독 상태에 두고 Chargebee는 dunning 중에도 `active` 유지 — 어느 쪽이든 결제 실패와 서비스 정지는 별개 축. 외부 조회자(앱·제어 서버)는 이용권만 조회하고 결제 테이블을 읽지 않는다 → 결제 장애 시에도 마지막 확정 상태로 서비스 판단이 계속된다.

## 4. 날짜 3종
| 날짜 | 위치 | 답하는 질문 |
|---|---|---|
| 청구 기간 | 청구서 | 고객: "7월 이용료" |
| 발행일·만기일 | 청구서 | 미납 일수·유예 |
| 결제 확정일 → 청구서 `paid_at`에 복사 | 결제 → 청구서 | 정산: "8월에 들어온 돈" |
7월 청구서가 8월에 결제되면 고객 화면에는 7월, 정산에는 8월. 하나의 사실을 다른 축으로 본다. 청구서 1건 = 결제 1건 + 시도 N건이어야 "7월 청구서 아래 실패 2번, 성공 1번"이 나온다.

## 5. 청구 주기 기준일(anchor)은 날짜 정책이다 (금액이 아니다)
- 등록일 기준(Stripe 기본 `billing_cycle_anchor`): 9/14 등록 → 매월 14일.
- 고정일 기준(Recurly Calendar Billing): 첫 달 일할, 이후 매월 1일 등. CMS 출금일·다매장 합산 청구와 잘 맞는다.
- 하위 결정: 시간대, 29~31일 등록의 2월 처리, 일할 분모.

## 6. 청구서 발행 시점 = 결제 시도일 − 수단별 리드타임
카드 0일(결제하는 날 만든다), CMS는 출금 파일 마감 + 사전 안내(D−3), 가상계좌는 입금 안내(D−7). 미리 만들지 않는 이유: 그 사이 상품 구성이 바뀌어도 청구서는 불변이라 어긋난다.

## 7. 0원 청구서·무료 기간
"3개월 무료"는 별도 TRIALING 상태 대신 **100% 할인 0원 청구서를 매달 발행** → 결제 요청 없이 즉시 PAID → 이용권. 이유: 무료도 기록이 남고, 유료 전환이 같은 스케줄러에서 시작되고, 이용권 개방 경로가 하나. 영업 형태별 "무료"가 여러 종류면 할인 모델 하나로 전부 표현된다. (사업자 간 무상 공급의 부가세는 세무 확인.)

## 8. 금액 3종
`taxable_amount`(과세표준) / `total_amount`(세금 포함 총액 = Σ 분담) / `payable_amount`(고객이 자기 수단으로 실제 부담). 제휴쿠폰·포인트가 들어오면 셋이 갈라진다. → [[에누리와 청구할인]]
