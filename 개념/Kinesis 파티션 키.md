# Kinesis 파티션 키 #stub

> [[핫 파티션]](DynamoDB 쪽 같은 개념) · [[이벤트 순서 보장]] · [[Kinesis 컨슈머]] · [[DynamoDB 파티션 키]] 와 연결.

## 1. 역할 — 라우팅 키이지 식별자가 아니다
파티션 키를 MD5 해시해 샤드에 배정한다. 같은 키 → 같은 샤드 → 그 샤드 안에서 **도착 순서**로 처리된다. 파티션 키가 정하는 것은 두 가지뿐:
1. **분산** — 키가 다양할수록 샤드에 고르게 퍼짐
2. **순서 단위** — "이 키의 이벤트끼리는 순서가 유지된다"

레코드의 정체성은 별도 ID(예: [[UUID v7]])가 맡는다. 파티션 키가 우연히 겹쳐도(사용자 12와 기기 12가 둘 다 `2#12`) 정합성엔 영향이 없고, 두 흐름이 한 샤드에 섞일 뿐이다.

## 2. 설계 — "순서가 필요한 단위"를 키로
- 순서가 필요한 단위가 사용자면 사용자 ID, 기기면 기기 ID. **여러 서비스가 각자 사용자 테이블을 가지면 ID가 충돌하므로 네임스페이스(서비스 ID)를 결합**한다: `서비스#사용자`
- 웹/앱 같은 **클라이언트 구분은 키에 넣지 않는다.** 같은 사용자가 웹·앱을 번갈아 쓰면 행동이 두 샤드로 갈려 사용자별 순서가 깨진다
- 대상이 여러 종류(사용자·기기)이고 둘 다 숫자 ID면 **타입 접두어**로 구분: `서비스#u#12` / `서비스#d#타입-7`. 라우팅엔 무해하지만 키의 자기 설명성과 향후 키 기반 필터링에 대비
- 대상이 없는 이벤트(기기가 스스로 낸 이벤트 등)는 폴백 키를 규약으로 강제한다. 폴백을 안 넘기면 `anonymous` 하나로 몰려 샤드 하나가 핫스팟이 된다

## 3. 샤드가 1개일 때
파티션 키는 사실상 **확장 대비 설계**다. 모든 키가 한 샤드로 가니 분산 효과는 없고, 나중에 샤드를 늘렸을 때 같은 키가 같은 샤드로 가는 성질(리샤딩 후에도 유지)만 남는다. 그래서 샤드 1개여도 키는 처음부터 제대로 잡아야 한다.

## 4. 핫 파티션
헤비 사용자(관리자·설치 작업자 계정)가 한 샤드로 몰리면 그 샤드만 스로틀. 대응은 [[핫 파티션]]과 같다 — 키에 시간 버킷 등을 섞어 카디널리티를 올린다(대신 그 대상의 순서 보장은 버킷 단위로 좁아짐).

## 복습 질문 #flashcards
- 파티션 키가 정하는 두 가지는? :: 샤드 분산과 순서 단위. 레코드 정체성은 아님.
- 클라이언트(웹/앱)를 키에 넣으면 안 되는 이유는? :: 같은 사용자의 행동이 두 샤드로 갈려 사용자별 순서가 깨짐.
- 서비스 ID를 사용자 ID에 결합하는 이유는? :: 서비스마다 사용자 테이블이 달라 ID만으로는 다른 사람이 같은 키가 됨.
