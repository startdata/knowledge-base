# SheetJS 메모리 모델 — xlsx 변환은 왜 데이터의 몇 배를 쓰나 #stub

> [[Node.js 메모리 오류 3종]] · [[대용량 내보내기 메모리 전략]] 와 연결.

## 1. 핵심
SheetJS(`xlsx` 패키지, Community Edition)는 **워크북 전체를 메모리에 올린 뒤 XML 문자열로 만들고 zip으로 묶는다.** 행 단위로 흘려보내는 xlsx 스트리밍 쓰기가 없다. 따라서 데이터 양에 비례해 힙이 커지며, 힙을 늘려도 상한은 반드시 존재한다.

## 2. 변환 한 번에 데이터가 몇 벌 생기나 (DB → xlsx 흐름 기준)
1. **DB 드라이버 결과** — 행마다 객체, 컬럼값마다 문자열·Date 인스턴스 (같은 매장명이라도 행마다 별도 문자열)
2. **호출자의 누적 배열** — 청크로 조회해도 끝에 합치면 1번이 전부 유지
3. **AOA(array of arrays) 변환** — 헤더 순서로 다시 만든 배열. 두 번째 복제
4. **`aoa_to_sheet`** — 시트는 `"A1"`, `"B1"` 같은 **셀 주소 문자열을 키로 갖는 객체**, 값은 셀마다 `{t, v}` 객체. 행×컬럼 개수만큼 객체+키 문자열 생성. **가장 큰 단계**
5. **`XLSX.write`** — 시트를 XML 문자열로 직렬화(수십 MB 문자열) → zip 압축 → Buffer

1~5가 동시에 살아 있는 순간이 있어 피크는 원본 데이터의 수 배. 경험적으로 컬럼 12개 기준 **행당 5~6KB**, 9만 행에 약 500MB.

## 3. 비용을 결정하는 것은 "행 수"가 아니라 셀 수 × 문자열 길이
- 같은 행 수라도 컬럼이 절반이면 비용도 절반 근처
- 한글 등 긴 문자열 컬럼이 많으면 더 커짐
- 임계값을 "행 수"로 둘 때는 타입별 컬럼 수를 감안해 여유를 크게 둔다

## 4. 대안
- **CSV 스트리밍 폴백** — 행 수/셀 수 임계값 초과 시 xlsx를 포기하고 파일에 바로 흘려 쓴다. 메모리는 임계값 이하로 고정 → [[대용량 내보내기 메모리 전략]]
- ExcelJS의 streaming writer(`stream.xlsx.WorkbookWriter`)는 행 단위 xlsx 쓰기를 지원 ? — 라이브러리 교체 비용과 함께 검토 (검증 필요)

## 복습 질문 #flashcards
- SheetJS xlsx 쓰기에서 메모리가 가장 많이 드는 단계는? :: `aoa_to_sheet`. 셀마다 주소 키 문자열 + `{t,v}` 객체를 만든다.
- 힙을 늘리면 SheetJS xlsx 대용량 문제가 해결되나? :: 아니다. 워크북 전체를 메모리에 올리는 구조라 상한이 옮겨질 뿐, 데이터 양에 비례해 언젠가 다시 터진다.
- 임계값을 행 수로 두면 부족한 이유는? :: 실제 비용은 셀 수×문자열 길이. 컬럼 수·문자열 길이가 다른 타입은 같은 행 수에서도 비용이 다르다.
