# 이중기입 원장 (Double-Entry Ledger) #stub

> [[결제 대사]] · [[멱등성]] · [[복합결제 전부-또는-전무]] 와 연결.
> 세션: [[세션/leaf-결제개편/설계결정-서사]]

## 1. 세 객체
Account(가치 풀: 고객 지갑, 보통예금, 미수금), Entry(계정의 변화), Transaction(원자적 금전 이동, 최소 2개 Entry). 모든 거래는 차변·대변 쌍이고 합은 항상 0. 1원이 사라지면 누군가 정확히 1원을 더 가진 것이 드러난다(Square "1센트 손실 → 1센트 이득 보장").

## 2. Append-only, 정정은 반제로
전표는 INSERT만. UPDATE/DELETE 대신 **반대 전표(반제) + 올바른 전표**를 추가한다. 한 번이라도 UPDATE로 고치면 그 시점 이후 "왜 이 숫자인가"에 답할 수 없다. Airbnb는 "이중기입은 형식이 아니라 런타임 불변식"이라 표현. 구현: DB 트리거로 UPDATE/DELETE 차단 또는 계정 권한.

## 3. 잔액은 파생물
`account_balance`는 캐시다. 진실은 전표이고 원장만으로 100% 재생성돼야 한다. Modern Treasury는 pending(확정 전, 수정 가능) / posted(확정, 불변) 두 단계.

## 4. 원장 write는 단 하나의 경로
`LedgerPostingService.post()` 외에 전표 테이블에 직접 INSERT하는 코드가 하나라도 생기면 모든 검증이 무의미해진다. 이벤트 소비자도 전표를 직접 넣지 않는다.

## 5. 마감 후 소급 금지
마감된 기간에 전표를 넣으면 확정된 재무 수치가 바뀐다. 당월 전표로 반제 + 재기표. 회계 기간 상태 검사가 없으면 조용히 일어난다.

## 6. 결제 시스템에서 원장은 몇 개인가
결제 모듈의 시도 기록(외부와 오간 사실), 월렛 모듈의 잔액 원장(포인트·캐시가 움직인 사실), 정산 모듈의 회계 원장(전표). 앞의 둘은 **사실의 기록**, 마지막은 **사실을 회계 계정으로 옮긴 것**. 정산은 앞의 둘을 직접 읽지 않고 이벤트를 받아 전표를 만든다. 두 잔액이 같은 것을 가리키면(선불충전금 부채 = 월렛 캐시 잔액 합) 일 대사로 맞춘다. → [[결제 대사]] [[선불전자지급수단 규제]]

## 7. 규모별 도구
MySQL 테이블 + 애플리케이션 규칙으로 충분한 규모(월 수만 전표 이하)와, 전용 원장 DB([[TigerBeetle]], Formance, Blnk)가 필요한 규모(초당 수만)는 다르다. 전용 DB는 운영 부담이 크고 배치 자유도를 잃는다.
