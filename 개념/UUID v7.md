# UUID v7 #stub

> [[멱등성]] · [[보조 인덱스]] · [[이벤트 순서 보장]] 와 연결.

## 1. 무엇인가
RFC 9562의 시간 기반 UUID. 앞 48비트가 Unix ms 타임스탬프, 나머지는 랜덤. 생성 시각 순으로 **문자열 정렬이 시간 정렬과 일치**한다(ms 해상도까지).

## 2. 왜 v4 대신 v7인가 — 인덱스 삽입 지역성
- v4(완전 랜덤)는 삽입마다 B-tree의 **임의 리프 페이지**를 건드린다. 인덱스가 버퍼 풀보다 커지면 삽입마다 디스크 읽기가 붙고 페이지 분할로 인덱스가 부풀어 오른다
- v7은 **우측 끝에 붙는다**(auto-increment와 비슷한 삽입 패턴) → 페이지 분할 없이 순차 삽입. PK나 UNIQUE 세컨더리 인덱스 모두 이득
- MySQL `CHAR(36)`(가독성) 또는 `BINARY(16)`(공간). PostgreSQL 네이티브 `UUID`는 16바이트 바이트 순 정렬이라 v7이면 그게 곧 시간순

## 3. 한계 — 정렬 키로 쓰지 말 것
- 시간 순서는 **밀리초까지만**. 같은 ms 안의 id들은 뒤 비트가 랜덤이라 생성 순서와 무관 (실측 확인됨)
- v7에 박히는 시각은 **생성(전송) 시각**이다. 백필처럼 "행동은 아까, 전송은 지금"이면 실제 발생 시각과 갈린다
- → 분석·정렬은 별도 `occurredAt` 컬럼. v7 정렬은 인덱스 지역성과 tie-break 용도

## 4. Snowflake와 비교
Snowflake(트위터식 64비트 시간+워커ID+시퀀스)는 8바이트로 더 작지만 **워커 ID를 프로세스마다 유일하게 배정하는 조정 인프라**(Redis/DB 시퀀스 등)가 필요하다. 워커 ID가 겹치면 조용히 중복 ID가 생기고, 그게 멱등 키면 서로 다른 이벤트를 같은 것으로 보고 **로그 없이 버린다.** 조정 인프라가 없으면 v7이 안전하다.

## 5. 어디서 발급하나
이벤트의 신원이 되려면 **이벤트가 기록되는 시점**(Outbox INSERT)에 한 번 발급하고, 재발송·재처리 때 다시 만들지 않는다. 여러 서비스가 같은 체계를 쓰도록 라이브러리 헬퍼로 통일 → [[Outbox 패턴]] §3

## 복습 질문 #flashcards
- v7이 v4보다 인덱스에 유리한 이유는? :: 시간순이라 B-tree 우측 끝에 순차 삽입돼 페이지 분할·랜덤 I/O가 없음.
- v7을 정렬 키로 쓰면 안 되는 이유 둘은? :: ms 해상도까지만 정렬 + 생성 시각이지 발생 시각이 아님.
- Snowflake 대신 v7을 고르는 상황은? :: 워커 ID를 조정할 인프라가 없을 때. 충돌 시 조용한 유실 위험.
