# Poison message (독성 메시지) #stub

> [[재시도 전략]] · [[Outbox 패턴]] · [[Kinesis 컨슈머]] · [[최종적 일관성]] 와 연결.

## 1. 무엇인가
컨슈머가 **어떻게 해도 처리할 수 없는 메시지.** 파싱 불가, 스키마 불일치, DB 제약 위반, 컨슈머 버그. 문제는 메시지 자체가 아니라 **그 메시지 때문에 뒤의 정상 메시지까지 막히는 것**(head-of-line blocking)이다.

- 수동 커밋(저장 성공 시에만 체크포인트) 구조에서 영구 실패 메시지가 배치에 끼면 → 같은 배치를 무한 재수신 → 파티션이 정체. 샤드/파티션이 하나면 파이프라인 전체가 멈춘다
- 릴레이(발행) 쪽도 같다. `ORDER BY id LIMIT n`으로 pending을 읽는데 맨 앞 행이 매번 예외를 던지면 뒤 행은 영원히 발송되지 않는다

## 2. 어디서 생기고 어디서 막나 — 층별

| 층 | 생기나 | 막는 방법 |
|---|---|---|
| **발행 전(기록 시점)** | 여기서 막으면 안 생김 | 스키마·크기 검증을 기록 시점에 → 잘못된 메시지는 트랜잭션과 함께 롤백 = **원천 차단** ([[Outbox 패턴]] §3) |
| **릴레이 → 브로커** | 드묾. 라이브러리 버전 차이, payload 손상 | **행 단위 격리**: 개별 try/catch로 실패 행만 `failed` 표시 + 알림, 나머지 계속. 브로커 부분 실패(레코드별 ErrorCode)는 재시도 |
| **컨슈머 → 저장소** | **진짜 발생지.** 구버전 스키마, DB 제약, 버그 | 실패 분류 + 격리 테이블 + 체크포인트 진행 |

## 3. 컨슈머의 실패 분류

| 종류 | 예 | 처리 |
|---|---|---|
| 일시적 | DB 연결 끊김, 타임아웃, 데드락, 락 대기 초과 | 체크포인트 넘기지 않고 backoff 재시도 |
| 영구적 | 파싱 실패, 필수값 누락, 컬럼 길이 초과, FK 위반 | **격리 테이블에 보관 → 체크포인트 진행 → 알림 → 수동 재처리** |

분류가 애매하면 일시적으로 보되 **같은 배치 재시도 상한(예: 10회)**을 두고 초과 시 영구로 간주한다. 상한이 없으면 정체를 못 막는다. → [[재시도 전략]]

## 4. 격리 저장소 — DLQ vs DB 테이블
- 큐 시스템(SQS 등)은 DLQ가 표준. Kafka는 Error Topic 관행. Kinesis는 기본 DLQ가 없다(Lambda ESM은 on-failure destination)
- **재처리 목적**이면 DB 테이블이 낫다: 실패 건은 극소수라 스트림이 과하고, 사람이 원인을 보고 수정·재실행해야 하니 조회·수정이 되는 저장소가 맞다. 스트림에 두면 그걸 읽는 컨슈머가 또 필요하다
- **모니터링 목적**(여러 서비스의 에러 현황을 한곳에서)이면 Error Topic이 맞다
- 격리 저장소는 **단계별로 하나씩**: 릴레이 실패는 outbox의 `status`, 컨슈머 실패는 `failed_events`
- 격리 테이블이 있어야 대사 배치가 "영구 거부된 이벤트"를 제외할 수 있다. 없으면 대사가 매일 재발송하고 컨슈머가 매일 거부하는 루프

## 5. 멱등과의 관계
격리했다가 재처리하는 것도 at-least-once의 한 형태라 저장은 멱등해야 한다. 격리 테이블 자체도 이벤트 ID UNIQUE로 두면 같은 이벤트가 두 번 격리돼도 한 건 → [[멱등성]]

## 복습 질문 #flashcards
- poison message의 진짜 해악은? :: 메시지 하나가 아니라 뒤의 정상 메시지까지 막는 head-of-line blocking.
- 세 층 중 원천 차단이 가능한 곳은? :: 발행 전 기록 시점 검증. 트랜잭션과 함께 롤백.
- 일시적 실패와 영구적 실패의 처리 차이는? :: 일시적은 체크포인트 안 넘기고 재시도, 영구적은 격리 후 체크포인트 진행.
- 재처리 목적 격리 저장소로 DB 테이블이 스트림보다 나은 이유는? :: 극소수·수동 재처리라 조회·수정이 되는 저장소가 맞고, 스트림은 읽는 컨슈머가 또 필요.

## 6. DLQ 오브젝트에는 무엇을 담나 — 레코드 식별자와 "영구 실패만" (2026-09-17 추가)
> 세션: [[세션/씨드앤-액션이력-파이프라인/BE-570-컨슈머-차단재시도]] · [[재시도 전략]]

- **레코드 식별자를 본문에 평문으로 넣는다** (`itemKey` = 매핑의 파티션 키 속성 값, 예 `eventId`). 원본 payload를 Base64로만 보관하면 대사(reconciliation)가 격리 목록을 만들 때 오브젝트마다 디코드·파싱해야 한다. 브로커의 파티션 키(`partitionKey`)와는 다른 값이라 둘 다 둔다. 디코드 실패 건은 `null`
- **일시 실패를 격리하지 않으면 DLQ 규칙이 단순해진다.** DLQ에 있는 것이 전부 영구 실패라면 대사는 "DLQ에 있으면 제외" 한 줄이다. 일시 실패가 섞이면 `errorMessage`로 사람이 가려야 하고, 재적재 전까지 정상 레코드가 조용히 빠진다 → [[재시도 전략]] 차단 재시도
- 격리 저장소 키 구조는 바꾸지 않는다 — 다른 컨슈머가 같은 DLQ 버킷을 쓰면 키 변경은 전부의 변경이다. 필드 추가는 가산적이라 안전
- 격리 저장소가 파일/오브젝트 스토리지(S3)면 DB 테이블(§4)과 달리 조회·수정이 불편하다. 그 대신 대사 배치가 읽기 쉽게 **본문에 필요한 키를 다 넣어 두는 것**으로 보완한다
