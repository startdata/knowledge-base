# 헬스체크 설계

## 원칙 1: 헬스체크 = 엔드포인트 + 호출하는 쪽
헬스체크 API가 있어도 **주기적으로 호출하는 쪽(모니터)이 없으면 감시가 안 되는 것**이다. 둘 다 있어야 한다.
- 엔드포인트: "정상인지"를 제대로 판단해야 한다.
- 모니터: 주기적으로 부르고, 실패하면 알린다.

## 원칙 2: 감시 대상 **밖에서** 확인한다
- 같은 서버의 cron이 자기 자신을 확인하면, 서버가 죽을 때 확인하는 쪽도 같이 죽는다.
- 같은 리전 Lambda만으로 감시하면 리전 장애 때 둘 다 멈출 수 있다.
- 사용자와 같은 경로(도메인 → HTTPS → 프록시 → 앱)로 확인해야 인증서·DNS·nginx 문제까지 잡힌다.
- 실무에서 흔한 조합: 로드 밸런서 헬스체크(있으면) + 외부 모니터(UptimeRobot, Pingdom, [[Route 53 상태 검사]] 등).

## 원칙 3: 무엇을 확인할지 정한다 (liveness vs readiness)
| 종류 | 확인 | 실패 시 의미 |
|---|---|---|
| liveness | 프로세스가 응답하는가 | 앱 재시작이 필요 |
| readiness | 의존성(DB 등)까지 쓸 수 있는가 | 트래픽을 받으면 안 됨 |

- 외부 모니터 하나만 쓴다면 **DB까지 확인**해야 "사용자가 서비스를 못 쓰는 상황"을 잡는다.
- 단, 로드 밸런서가 이 경로로 인스턴스를 빼거나 교체한다면, DB 장애 때 **모든 인스턴스가 빠지는** 연쇄를 고려해야 한다(그래서 쿠버네티스는 liveness와 readiness를 나눈다).

## 구현 요령
- **DB 확인은 짧은 타임아웃**을 둔다. 커넥션 풀 대기(예: Sequelize 기본 60초)에 묶이면 모니터 쪽이 먼저 타임아웃 난다. → [[커넥션 풀 크기 산정]]
- 타임아웃용 타이머는 정리한다(`clearTimeout`). 안 하면 요청마다 타이머가 남고 테스트가 안 끝난다.
- **실패를 예외로 던지지 말고 상태 코드만 503으로** 바꾼다. 예외 필터를 타면 장애 동안 매 호출마다 에러 로그·에러 알림이 쌓인다. 헬스체크 실패 알림은 모니터가 담당하도록 경로를 나눈다. → [[에러 알림 설계]]
- 응답 본문에 **어디가 문제인지**(`db: down`)를 담는다.
- 헬스체크 요청은 **요청 로그에서 뺀다.** 모니터가 분당 수십 번 부르면 로그가 불어난다.
- 응답은 최소한으로 (공개 경로라 내부 정보 노출 금지).

#flashcards
- Q: 헬스체크 API가 있는데 장애를 못 알아챈 이유가 될 수 있는 것? → A: 호출하는 모니터가 없음.
- Q: DB 장애 시 헬스체크에서 예외를 던지지 않고 503만 반환하는 이유? → A: 예외 로그·에러 알림이 매 호출마다 쌓이는 걸 막고, 알림은 모니터가 담당하도록.
- Q: 헬스체크 DB 확인에 타임아웃이 필요한 이유? → A: 커넥션 풀 대기에 묶여 모니터가 먼저 타임아웃 나는 걸 막기 위해.
