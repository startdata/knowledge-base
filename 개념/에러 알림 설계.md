# 에러 알림 설계 (앱 → Slack)

서버 에러를 채팅 채널로 보낼 때의 기준. "죽었다/살아났다"는 헬스체크 모니터가, **"무엇 때문에"는 앱의 에러 알림**이 담당한다.

## 무엇을 보낼까 — 5xx만
- 4xx(로그인 실패, 잘못된 요청)까지 보내면 알림이 너무 많아져서 결국 무시하게 된다(alert fatigue).
- 5xx는 "서버 쪽 문제"라 대부분 알아야 한다.
- 운영 환경에서만 보낸다(로컬·개발 제외).

## 폭주 방지 — 같은 에러 쿨다운
- DB 장애처럼 모든 요청이 5xx가 되면 알림이 폭주하고, Slack Incoming Webhook의 전송 제한(대략 초당 1건)에도 걸린다.
- 같은 에러(`에러명:메시지`)는 N분에 한 번만 보낸다. 프로세스 메모리의 Map으로 충분하다(단일 프로세스).
- 키에 요청 경로를 넣으면 ID가 섞여(`/items/123`) 키가 무한히 늘어난다. 메시지에도 입력값이 섞일 수 있으니 **Map 크기 상한**(예: 100개 넘으면 비우기)을 둔다.

## 개인정보 최소화
- 요청 본문, IP, **쿼리스트링**(OAuth `code`, 토큰이 들어갈 수 있음)은 보내지 않는다.
- 메서드, 경로, 에러명, 메시지, 스택 앞부분만.
- 에러 메시지·스택에도 사용자 입력이 섞일 수 있어 완전한 차단은 아니다 → 채널을 운영자 전용(비공개)으로 둔다.

## 전송 방식 — 응답을 막지 않는다
- fire-and-forget: 전송을 `await`하지 않는다. Slack이 느리거나 실패해도 사용자 응답은 지연되지 않게 한다.
- 전송에도 타임아웃(예: 3초)을 건다. → [[트랜잭션 안 외부 호출]]
- 실패는 로그로만 남긴다.

## 헬스체크와 경로를 나눈다
헬스체크의 DB 실패를 예외로 던지면 이 알림 경로를 타서 매 호출마다 알림이 쌓인다. 헬스체크는 상태 코드(503)만 바꾸고, 알림은 모니터가 담당한다. → [[헬스체크 설계]]

- Q: 에러 알림에서 4xx를 빼는 이유? → A: 알림 과다 → 무시하게 됨(alert fatigue).

- Q: 알림에서 쿼리스트링을 빼는 이유? → A: OAuth code·토큰이 들어갈 수 있음.
