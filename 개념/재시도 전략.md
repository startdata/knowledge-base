# 재시도 전략 (Retry)

## 오류 분류 — 무엇을 재시도할 것인가
- **일시적(transient)**: 502, 타임아웃, 일시적 네트워크 → 재시도 **가치 있음**.
- **영구적(permanent)**: 400(잘못된 요청), 파싱 불가 → 재시도해도 같은 실패 = **낭비**.
→ "무조건 N회 재시도"는 안티패턴. 상태코드/오류 종류로 분기해야 한다.

## ⚠️ 재시도 안전성 = 요청의 멱등성
재시도하려면 **그 요청이 멱등**이어야 안전.
- 조회성 GET/POST: 여러 번 보내도 서버 상태 불변 → 안전.
- 비멱등(결제 생성 등): 재시도 = 중복 결제 → 멱등키/중복 검사 선행 필수.
- **재시도를 넣기 전 반드시 물을 질문: "이 요청은 멱등인가?"** ([[멱등성]])

## 백오프 (backoff)
- **횟수**와 **간격**은 다른 축. 횟수만 두고 간격 0이면 = 백오프 없음(즉시 재시도).
- **지수 백오프 + jitter**: 재시도 간격을 점점 늘리고(2^n) 무작위화.
  - 이유: 죽어가는 서버에 재시도 폭주(thundering herd)를 막고 회복 시간을 줌. jitter는 여러 클라이언트의 재시도가 동시에 몰리는 것을 분산.
- 생략 가능한 경우: 모의/즉시응답 환경, 요구가 횟수만 규정. **실서비스는 사실상 필수.**

## 메시지 컨슈머의 재시도 — 배치 상한이 필요하다 (2026-09 추가)
스트림 컨슈머(Kinesis·Kafka)는 저장 성공 시에만 체크포인트를 넘기므로, 실패하면 같은 배치를 다시 받는다. 여기서 transient/permanent 분류를 안 하면 영구 실패 메시지 하나가 배치 전체를 무한 재수신시켜 파이프라인이 멈춘다([[Poison message]]).
- 일시적(DB 연결·타임아웃·데드락): 체크포인트 넘기지 않고 backoff 재시도
- 영구적(파싱·제약 위반): 즉시 격리 테이블로 → 체크포인트 진행
- 분류가 애매하면 일시적으로 보되 **같은 배치 재시도 상한**(예: 10회)을 두고 초과 시 영구로 간주. 상한이 없으면 정체를 못 막는다
- 재시도 중 5분이 넘으면 Kinesis 이터레이터가 만료되니 체크포인트에서 재발급하는 경로가 있어야 한다 → [[Kinesis 컨슈머]]

## 결제 재시도 (2026-09 추가)
> [[멱등성]] 재전송 vs 재시도 · [[결제 상태 기계]] · 세션: [[세션/leaf-결제개편/설계결정-서사]]

- **거절 분류**: hard(카드 정지·분실·만료 → 자동 재시도 대상 아님, 수단 교체 요청) / soft(한도·잔액·일시 오류 → 정책에 따라 재시도). PG 응답 코드로 갈린다.
- **타임아웃은 재시도하지 않는다.** 상태를 "모름"으로 두고 조회 → 승인됐으면 확정, 없으면 **같은 키로 재전송**. PG가 문서화한 타임아웃 확정 시간 전에는 실패로 내리지 않는다. 여기서 새 키로 재시도하면 이중 승인이다.
- **재시도 정책(dunning)은 데이터로**: 수단별 횟수·간격·소진 시 동작(유예·정지)을 테이블에 두고 코드는 읽기만. 정책이 미정이면 "자동 0회 + 관리자 수동"으로 시작하고 값만 바꾼다.
- **자동과 수동은 같은 경로**: 트리거(SCHEDULE / AUTO_RETRY / MANUAL / CUSTOMER_UPDATE)와 행위자만 다르고 결제 모듈은 구별하지 않는다. 그래야 멱등키 하나로 둘이 동시에 오는 것을 막는다.
- 고객이 결제수단을 갱신하면 예약된 재시도를 취소하고 즉시 재시도한다.
- 소진 시 서비스 정지 여부는 결제가 아니라 이용권(정책) 쪽이 결정한다. → [[구독 청구 도메인 모델]]

출처: [Stripe Smart Retries](https://docs.stripe.com/billing/revenue-recovery/smart-retries), [Chargebee Subscriptions(dunning)](https://www.chargebee.com/docs/billing/2.0/subscriptions/subscriptions)

## 상한 있는 재시도 vs 상한 없는 차단 재시도 (2026-09-17 추가)
> [[Kinesis 컨슈머]] §6 · [[Poison message]] · [[Java 스레드 인터럽트]] · 세션: [[세션/씨드앤-액션이력-파이프라인/BE-570-컨슈머-차단재시도]]

위 "배치 상한이 필요하다"는 **재전달을 누가 해 주느냐**에 따라 뒤집힌다.

| 재전달 주체 | 예 | 실패 처리 |
|---|---|---|
| 브로커/플랫폼이 다시 준다 | SQS(visibility timeout), Kafka(커밋 안 하면 재소비), Lambda ESM(bisect·재시도) | 상한 두고 초과 시 DLQ. 정체는 플랫폼 재전달이 막아 준다 |
| **내가 위치를 지켜야 한다** | KCL(예외 던지면 배치 skip), 직접 폴링 | **일시 실패는 상한 없이 성공까지 차단**. 상한을 두면 긴 장애에서 정상 레코드가 대량 격리되고, 격리를 안 하고 예외를 던지면 유실이다 |

차단 재시도를 택할 때의 규칙:
- **분류가 전부다.** 영구 실패(제약 위반·문법·파싱)는 즉시 격리, 일시 실패(연결·데드락·타임아웃·실행 중 절단)는 무한 대기. 여기서 일시 실패를 하나 놓치면(예: [[Spring DataAccessException 계층]]의 `RecoverableDataAccessException`) 그 경로만 조용히 격리된다
- **`max-retries`의 의미가 바뀐다.** "몇 번 뒤 포기"가 아니라 **백오프가 최대치에 도달해 고정되는 시점**. 같은 설정 키가 DynamoDB 경로(상한 후 DLQ)와 RDS 경로(차단)에서 다른 뜻이면 문서에 반드시 적는다
- **로그 스로틀.** 무한 루프는 무한 로그다. 상한 이전은 WARN 매번, 이후는 N회마다 ERROR 1줄(`attempt % 30`). 최대 백오프가 20초면 30회는 10분이다 — 주석의 "≈1분"은 백오프 값에 따라 틀린다
- **관측은 카운터로.** 차단 중엔 처리량·지연 지표가 멈추거나 마지막 값에 머무니, 재시도마다 올라가는 카운터(Sum > 0 알람)를 둔다
- **인터럽트는 실패가 아니다.** shutdown이 차단 루프를 깨우면 DLQ도 체크포인트도 하지 않고 빠져나온다
- 격리 저장소(DLQ)에 **쓰는 것도 차단**해야 한다. 격리조차 못 하는 상태에서 예외를 내면 배치 전체가 유실된다
- 대가: 영구적인 S3 403/404 같은 것도 무한 차단이 된다 — 알람이 상한의 역할을 한다

#flashcards
- Q: 재시도 상한을 둘지 무한 차단할지 가르는 기준은? → A: 재전달을 브로커가 해 주는가(상한+DLQ) vs 내가 위치를 지키는가(차단).
- Q: 차단 재시도에서 `max-retries`의 의미는? → A: 포기 시점이 아니라 백오프가 최대치에 고정되는 시점.
