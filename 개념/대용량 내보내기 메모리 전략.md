# 대용량 내보내기 메모리 전략 — 날짜 청크 · 행 기준 폴백 · 스트리밍 #stub

> [[Node.js 메모리 오류 3종]] · [[SheetJS 메모리 모델]] 와 연결.

## 1. 문제의 형태
"조회 → 전부 모음 → 한 번에 변환 → 응답"은 데이터 양에 비례해 힙이 커진다. 조회를 쪼개도 **결과를 다시 합치면 메모리는 줄지 않는다.** 청크 조회는 DB 부하·쿼리 타임아웃 대책이지 메모리 대책이 아니다.

## 2. 세 층의 대책

| 층 | 대책 | 무엇을 해결하나 | 한계 |
|---|---|---|---|
| 조회 | 날짜 등 **범위 기준 청크** | 쿼리 1회 부하·타임아웃 | 결과를 누적하면 메모리 그대로 |
| 출력 형식 | **행 수 임계값 초과 시 스트리밍 형식(CSV)으로 폴백** | 메모리를 임계값 이하로 고정 | 사용자가 받는 형식이 바뀜 |
| 런타임 | 힙 상한 상향 | 여유 확보 | 구조가 비례형이면 상한만 옮겨짐. 컨테이너 한도 확인 필수 |

## 3. 행 기준 폴백의 두 구현
1. **중간 전환** — 청크 루프에서 누적 행 수가 임계값을 넘는 순간 스트리밍 라이터를 열고, 쌓인 행을 먼저 쓴 뒤 남은 청크는 바로 흘림. 추가 쿼리 없음, 분기 조금 증가. 응답의 파일명·Content-Type을 **서비스가 마지막에 결정**하는 구조여야 가능
2. **사전 COUNT** — 루프 전에 `COUNT(*)`로 판단해 처음부터 형식 결정. 코드 단순. 큰 테이블에선 COUNT 자체가 수 초 비용

날짜 기준 임계값은 보조로 남긴다. 데이터 밀도(센서 수 등)가 달라 날짜만으로는 재발한다.

## 4. 임계값 산정
- 실측 크래시 지점의 **1/3 이하**. 이유: ① 동시 요청이 힙을 나눠 씀 ② 컬럼 수·문자열 길이가 타입별로 달라 행당 비용이 흔들림 ③ 변환 피크는 누적분의 수 배
- 정확히 하려면 단계마다 `process.memoryUsage().heapUsed`를 찍어 행당 비용 측정 후 역산
- 메모리 가드(요청 진입 시 힙 사용률 체크)가 있으면 그 기준과 맞물리게 조정

## 복습 질문 #flashcards
- 날짜 청크 조회가 힙 부족을 막지 못하는 이유는? :: 결과를 누적해 한 번에 변환하면 메모리는 전체 양 그대로. 청크는 DB 부하 대책.
- 중간 전환 방식 폴백이 가능하려면 API 구조에 필요한 조건은? :: 파일명·Content-Type을 서비스가 처리 끝에 결정하고 컨트롤러가 그대로 쓰는 구조.
- 임계값을 크래시 지점의 1/3 이하로 두는 이유 셋? :: 동시 요청 분할, 타입별 행당 비용 편차, 변환 피크가 누적분의 수 배.
