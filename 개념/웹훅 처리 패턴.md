# 웹훅 처리 패턴

> [[멱등성]] · [[이벤트 순서 보장]] · [[결제 상태 기계]] · [[Outbox 패턴]] 와 연결.
> 세션: [[세션/leaf-결제개편/설계결정-서사]]

## 1. 웹훅은 at-least-once이고 순서가 뒤바뀐다
PG는 응답을 못 받으면 재전송한다(토스페이먼츠 가상계좌: 최대 7회·약 3일 19시간, Stripe: 3일간 지수 백오프). 같은 이벤트가 여러 번, 취소 웹훅이 승인 웹훅보다 먼저 올 수 있다.

## 2. 처리 순서 (Stripe·Adyen 공통 권고)
0. IP 허용 목록·레이트 리밋 (인증 없는 공개 엔드포인트)
1. 서명(HMAC) 검증
2. **원본을 저장** — `(provider, event_key)` 유니크. 중복도 저장하고 처리만 스킵(중복 건수 자체가 PG 이상 징후)
3. 중복이면 200 반환 후 종료
4. **200을 먼저 반환** (밀리초 단위)
5. 실제 처리는 비동기 워커에서

## 3. 이벤트 ID가 없는 PG
모든 PG가 고유 이벤트 ID를 주지 않는다. 없으면 `(결제 키, 상태, 업체 이벤트 시각)` 해시를 대체 키로. PG 선정 시 확인 항목.

## 4. 서명이 없는 PG
저장 후 **조회 API로 본문을 대조**한다. 토스페이먼츠 v1 웹훅처럼 서명 대신 IP 허용 + 조회 재확인을 권하는 경우가 있다(확인 필요).

## 5. 웹훅은 보조 채널이다
동기 응답으로 이미 확정된 건의 웹훅은 무처리. 비동기 수단(가상계좌·CMS)에서는 웹훅이 주 채널이지만, 유실에 대비해 **조회 API·대사와 병행**한다. 웹훅만 믿지 않는다.

## 6. 순서 역전
허용 전이표로 검증해 맞지 않는 전이(승인 전 취소)는 **보류 큐**에 넣고 짝이 오면 처리. 보류 최대 횟수·시간을 두고 소진 시 대사 대상으로 전환(종료 조건 없으면 영원히 보류).

## 7. 우리가 요청하지 않은 웹훅
PG 콘솔 직접 취소, 카드 분쟁(차지백, 수개월 후)은 우리 요청 없이 온다. `source=EXTERNAL / DISPUTE`로 시스템이 행을 생성하고 상태를 맞춘다. 이용권 소급 종료가 필요할 수 있다.
