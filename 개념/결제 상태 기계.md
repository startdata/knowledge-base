# 결제 상태 기계

> [[멱등성]] · [[재시도 전략]] · [[Outbox 패턴]] · [[웹훅 처리 패턴]] · [[복합결제 전부-또는-전무]] 와 연결.
> 세션: [[세션/leaf-결제개편/설계결정-서사]]

## 1. 결제는 요청-응답이 아니라 시간을 두고 바뀌는 상태다
카드 승인은 수 초지만 매입·청산·정산·입금은 며칠, 분쟁은 수개월 뒤다. CMS는 요청이 일괄이고 결과가 익일, 가상계좌는 고객이 언제 입금할지 우리가 정하지 못한다. 그래서 "성공/실패" 두 값이 아니라 **상태 기계**가 필요하고, 전이는 우리가 일으키는 것(요청)과 외부가 알려주는 것(응답·웹훅·정산 명세)이 섞여 있다.

## 2. 상태 집합은 하나, 수단별 경로는 다르게
수단마다 별도 모델을 만들면 결제 전체 상태를 합성하는 규칙이 수단 조합 수만큼 생긴다. 집합은 하나로 두고 수단별 허용 경로만 다르게 하면 새 수단이 와도 합성 규칙은 그대로다(토스페이먼츠·Stripe 모두 이 방식).

| 수단 | 경로 |
|---|---|
| 빌링키 카드 | 대기 → 처리중 → 확정 / 실패 |
| 포인트·캐시(내부) | 대기 → **선점(HELD)** → 확정 / 해제 |
| CMS | 대기 → 출금요청됨 → 확정 / 실패 (트리거: 출금 결과 수신) |
| 가상계좌 | 대기 → 입금대기 → 확정 / 만료 |

**"승인(선점)" 상태가 왜 있는가**: 국내 빌링키 카드는 한 번의 호출로 승인과 매입 요청이 끝나 선점을 거치지 않는다. 필요한 곳은 (1) 월렛 복합결제(포인트를 잡아두고 카드 성공 시 확정, 실패 시 해제) (2) 해외 PG의 승인·매입 분리(Stripe `requires_capture`, Adyen Authorised). 카드 "승인"과 혼동을 피해 이름을 `HELD`로.

## 3. 불확실 상태는 실패가 아니다
응답을 못 받았을 때 실패로 처리하고 새 요청을 보내면 이중 승인이다. `PROCESSING`(모름)을 명시적 상태로 두고, 조회 API·웹훅·대사로 확정한다. 확정 전엔 재시도 금지, 같은 키 재전송만 허용. 토스페이먼츠 SUCCESS/FAILURE/UNKNOWN, 카카오페이 Success/Failure/Unknown이 같은 원리.

## 4. 결제 → 분담 → 시도의 3층
- **결제(payment)**: 청구서 1건에 대한 결제. 청구서와 1:1.
- **분담(tender)**: 결제를 구성하는 수단별 금액. 단일 수단이면 1행. 재시도 시 이전 분담 집합은 `SUPERSEDED`로 닫고 새 집합(수단이 바뀔 수 있음).
- **시도(attempt)**: 외부에 보낸 요청 1건. 재시도마다 1행, 재전송은 같은 행. Stripe의 PaymentIntent : Charge = 1 : N.

결제 상태는 분담 상태의 **합성**이다: 전부 확정 → 확정, 하나라도 대기 → 처리중, 하나라도 실패 → 나머지 선점 해제 + 이미 확정된 외부 분담이 있으면 `COMPENSATING`(보상 취소 중, 취소가 끝날 때까지 실패로 내리지 않음).

## 5. "단일 status 컬럼으로는 부족하다" (Square)
현재 상태만으로는 "왜 이렇게 됐나"에 답할 수 없다. 전이마다 이력 행(이전·이후·시각·원인 ID: attempt·webhook·관리자)을 남긴다. 부분 매입·다중 환불·분쟁·지연 정산이 전부 개별 금융 이벤트로 남아야 대사가 된다.

## 6. 허용 전이표와 동시 쓰기
동기 응답·웹훅·복구 조회 세 경로가 같은 행을 건드린다. 전이는 허용 전이표로 검증하고 `UPDATE … WHERE status = :expected AND version = :v` 영향 행 수로 확인한다. 허용되지 않는 전이(순서 역전)는 보류 큐. 관리자 수동 전이는 표에 별도 열거 + 증빙 필수.

- 국내 카드 결제에 선점(승인) 상태가 없는 이유는? :: 승인과 매입 요청이 한 번의 API 호출로 끝난다. 선점은 월렛과 해외 PG용.

## 실패는 세 종류다 — 안 나갔다 / 나갔다 / 모른다 (2026-09 추가)
> 세션: [[세션/leaf-결제개편/설계결정-서사]] · [[재시도 전략]] · [[멱등성]]

§3은 "모름"만 다뤘지만 그건 절반이다. 외부에 돈을 보내는 호출의 실패는 **어디서 실패했는지**에 따라 갈리고, 셋을 같은 FAILED로 뭉개면 양쪽으로 사고가 난다.

| 실패 지점 | 외부에서 실제로 일어난 일 | 같은 FAILED로 묶으면 |
|---|---|---|
| 보내기 전 검증에서 걸림 | 없음 | (안전) |
| 외부가 거절을 확정 | 없음 | (안전) |
| **응답을 못 받음(타임아웃)** | 승인됐을 수도 있음 | 재시도 → **이중 승인** |
| **승인 후 우리 기록에 실패** | 승인됨 | 실패로 보여 **돈은 나갔는데 서비스가 안 열림** |

앞의 둘은 외부에 부수효과가 없으니 자유롭게 재시도해도 된다. 뒤의 둘은 **조회로 확정하기 전까지 어떤 재시도도 금지**이고, 둘 다 같은 `PROCESSING` 행에 남아 복구 워커의 입력이 된다. 설계 순서는 "실패를 어디서 실패했는지로 먼저 나누고, 그 다음 각각의 상태와 재시도 가능 여부를 정한다"이다.

결제만의 이야기가 아니다. 외부에 되돌릴 수 없는 부수효과를 내는 연동(메일·문서 발급·외부 재고 차감)은 전부 같은 분류가 선다.

**시나리오를 나열할 때의 구간**: 요청 이전 / 요청 중 / 결과 수신 이후 / 재시도·후속. 사고는 코드가 아니라 "고려하지 않은 경우"에서 나므로 구간마다 감지 방법·남는 상태·처리·서비스 개방 영향을 빈칸 없이 채운다.

## 저장된 결제수단은 결제와 생명주기가 다르다 (2026-09 추가)
> [[한국 결제수단 특성]] · [[구독 청구 도메인 모델]] §1

결제(payment)·분담(tender)·시도(attempt) 3층과 **별개의 축**으로 결제수단(instrument)이 있다. 카드는 결제가 한 건도 없어도 만료·교체·해지되고, 결제는 수단이 바뀌어도 과거 기록이 그대로 남아야 한다.

- 둘을 한 테이블에 두면 **카드 교체가 과거 결제의 수단 표시를 바꾸거나, 해지된 카드로 재시도가 나간다.**
- 그래서 결제 행이 들고 있는 수단 정보는 참조가 아니라 **값 스냅샷**이다. 수단이 나중에 해지돼도 "그때 이 카드로 결제했다"는 사실은 보존된다.
- 수단 자체도 상태 기계다(등록 대기 → 활성 → 만료 / 해지). **등록 요청의 타임아웃도 결제와 똑같은 불확실 상태**이며 조회로 확정한다.
- 청구 주체당 수단은 여러 개이고 기본 수단은 수단 종류별(카드·계좌)로 따로 있을 수 있다.
- 수단 교체는 결제의 입력을 바꾸는 사건이다 → 미납 건이 있으면 즉시 재시도 트리거. → [[재시도 전략]]

Stripe(Customer ↔ PaymentMethod), Adyen(stored payment method)이 같은 구조다.

## 무엇을 행으로 남기는가 (2026-09 추가)
> [[결제 대사]] · [[헥사고날 아키텍처]] (어댑터가 기록을 책임진다)

기준은 하나다. **"이 청구서에 왜 돈이 들어왔나 / 왜 안 들어왔나"를 DB만 보고 답할 수 있어야 한다.** 분쟁·대사 불일치·감사는 몇 달 뒤에 오고, 그때 로그는 지워져 있거나 검색이 안 된다. 로그는 근거가 못 된다.

판정 규칙: **돈이 움직였을 수 있는 순간은 행으로, 움직이지 않은 것은 상태로.**

| | 남기는 형태 |
|---|---|
| 외부에 요청을 보냈다 (성공·거절·타임아웃 전부) | 시도 행 1개 + 요청·응답 원문 |
| 행만 만들고 호출 전에 죽었다 | 같은 행이 "처리중"으로 남음 → 복구 워커의 입력 |
| 보내기 전 검증에서 걸렸다 | **시도 행 없음.** 결제 상태 + 사유 코드로 충분 (외부에 아무것도 안 나갔다) |
| 외부에서 통지를 받았다 (중복 포함) | 수신 행 1개. 중복도 저장하고 처리만 스킵 |
| 상태가 바뀌었다 | 이력 행 1개 (원인 ID 포함) |
| 폴링했는데 할 일이 없었다 | **기록 없음** |

무엇을 **안 남길지**가 원칙의 절반이다. 전부 남기면 노이즈에 묻혀 "왜"에 답하지 못한다.

- 민감정보(카드번호·CVC·계좌번호)는 저장 전에 어댑터가 마스킹한다. 토큰·빌링키는 암호화 저장.
- **원문은 별도 테이블로 분리한다.** 보존 기간이 법무 확인 전이라 미정일 때, 나중에 그 테이블만 정리할 수 있다. 금액·상태·식별자는 영구 보존.

출처: Stripe는 시도마다 Charge를 남기고 토스페이먼츠는 결제 기록을 INSERT-only로 다룬다. 기준 문장과 "안 남기는 것" 구분은 설계 판단.
