# 모듈러 모놀리스 (Modular Monolith)

> [[헥사고날 아키텍처]] · [[Outbox 패턴]] · [[Kafka 파티션과 컨슈머 그룹]] 와 연결.
> 세션: [[세션/leaf-결제개편/설계결정-서사]]

## 1. 언제 택하나
모듈이 나중에 다른 서버로 갈 수 있는데(정산 → 어드민 서버, 결제 → 별도 서버) 지금은 배치를 결정할 수 없을 때. 처음부터 서비스를 나누면 서비스 수만큼 배포·모니터링·시크릿·네트워크가 필요하고 분산 디버깅을 감수해야 한다. 한 프로세스 안에서 **경계만 서비스처럼** 지키면 분리는 구현 교체가 되고, 지키지 않으면 재작성이 된다.

## 2. 경계 원칙 7개
| 원칙 | 어기면 |
|---|---|
| 테이블 소유권: 모듈은 자기 테이블만 읽고 쓴다. 타 모듈 테이블 JOIN·FK·SELECT 금지. 타 모듈 식별자는 값으로만 | 서버를 나누는 순간 쿼리가 깨짐 |
| 계약은 메시지: 버전 있는 직렬화 DTO. 객체 참조 넘기지 않음 | HTTP·큐로 바꿀 때 계약 재설계 |
| 나가는 이벤트는 outbox: 인메모리 이벤트(`EventEmitter2`)는 모듈 내부에서만 | 재시작 시 소실, 분리 시 경로 없음 |
| 들어오는 이벤트는 inbox: `(source, event_id)` 유니크 | 재전달 시 이중 처리 |
| 조회는 포트 뒤로: 인프로세스 구현 → 분리 후 HTTP 구현 | 분리 시 호출부 전부 수정 |
| 트랜잭션은 모듈 안에서만: 모듈 간 일관성은 이벤트 + 멱등 소비 + 대사 | 분리 시 분산 트랜잭션 필요 |
| 저장소 분리: 접두어는 최소. **물리적으로 막는 건 모듈별 DataSource와 DB 계정 권한** (MySQL은 같은 서버의 다른 스키마도 한 트랜잭션에서 접근 가능) | 어느 테이블이 누구 것인지 모름 |

## 3. 강제 수단 — 규율만으로는 한 달 안에 무너진다
- ESLint `no-restricted-imports`로 타 모듈 entity·repository import 차단
- 모듈별 TypeORM DataSource + DB 계정 GRANT
- 계약 DTO는 공용 위치(`contracts/`)에만
- 리뷰 체크리스트: 모듈 간 JOIN·FK 0개, 공유 트랜잭션 0개, outbox 없이 나가는 이벤트 0개

## 4. 서버 분리 시 바뀌는 것 / 바뀌지 않는 것
| 항목 | 바뀌는 것 | 바뀌지 않아야 하는 것 |
|---|---|---|
| 이벤트 전달 | 릴레이 목적지(인프로세스 → 브로커) | outbox·inbox, 계약 DTO, event_id |
| 동기 조회 | 포트 구현(함수 → HTTP + 인증·타임아웃·회로 차단) | 포트 인터페이스, 응답 DTO |
| DB | 별도 서버로 이전 | 소유권, 값 참조 |
| 추적 | 요청 ID → 분산 추적 | 요청 ID 전파 규칙 |
| 배포 | 서비스별 CI/CD | 계약 버전 호환(모르는 필드 무시) |

## 5. 비용 (정직하게)
- 같은 프로세스인데 이벤트가 outbox를 거쳐 수 초 뒤 도착. 배관 코드 증가.
- 배포 커플링(앱 배포마다 워커 재시작), 장애 동반(앱 API 문제가 배치를 멈춤), 보안 경계(웹훅·민감 테이블이 앱과 같은 DB 서버), 리소스 경합. 워커 프로세스 분리와 DB 계정 분리로 일부 완화.
- **가장 큰 위험은 두 가지**: 경계 규율 붕괴, 그리고 "나중에"가 오지 않아 이행이 일어나지 않는 것. 분리 트리거를 미리 정한다.

## 6. 절충: 경계별로 전달 수단을 다르게
가장 먼저 분리될 모듈(외부 호출·보안 격리가 필요한 결제)의 안팎만 처음부터 브로커(Kafka), 나머지는 같은 outbox에 인프로세스 릴레이 → 토픽별 설정으로 전환. 이벤트 발행 포트 하나에 구현 둘.

출처: 설계 판단. Kill Bill(서브시스템 경계, [문서](https://docs.killbill.io/)), 토스페이먼츠 "도메인이 원장을 직접 쿼리하지 않고 이벤트로만"([블로그](https://toss.tech/article/payments-legacy-5))을 참고.
