# 커넥션 풀 크기 산정

## 공식 — DB 서버 기준
```
적정 연결 수 ≈ (DB 코어 수 × 2) + 유효 디스크 수
```
- HikariCP 위키 "About Pool Sizing"에 소개된 PostgreSQL 쪽 경험식.
- 핵심: DB가 동시에 처리할 수 있는 양은 **CPU에 묶여 있다.** 연결을 더 늘리면 대기 장소가 앱에서 DB로 옮겨질 뿐이고, DB 안에서 컨텍스트 스위칭·락 경쟁으로 오히려 느려질 수 있다.
- 예: vCPU 2개 DB(`db.t4g.micro`) → 약 5.

## 실제 최대 연결 = 프로세스 수 × 풀 max
- PM2 클러스터·여러 인스턴스로 늘리면 곱으로 늘어난다. DB `max_connections`와 DB 메모리(연결마다 수 MB)를 넘지 않게 한다.
- 관리 도구(TablePlus 등) 접속도 DB 연결 수에 포함된다.

## 늘릴지 판단 — 두 지표를 같이 본다
| DB 연결 수 | DB CPU | 판단 |
|---|---|---|
| 평소 max 미만 | 낮음 | 그대로 |
| 자주 max에 붙음 | **낮음** | 풀 부족 → max 늘리기 |
| 자주 max에 붙음 | **높음** | DB 한계 → 늘려도 소용없음. 쿼리 개선·사양 업 |

## 풀을 고갈시키는 진짜 원인은 대개 "오래 붙잡는 코드"
- 쿼리 하나가 짧으면 5개로도 초당 많은 요청을 처리한다. 쿼리가 끝나면 연결은 바로 반납된다.
- 트랜잭션은 **커밋할 때까지** 연결을 붙잡는다. 트랜잭션 안에서 외부 API를 부르면 그 응답을 기다리는 동안 연결이 묶인다. → [[트랜잭션 안 외부 호출]]
- 외부 호출이 트랜잭션 **밖**에 있으면(예: AI 채점 API) 몇 초가 걸려도 연결을 잡지 않는다.
- 대용량 파일(음성 등)을 S3·CloudFront 서명 URL로 직접 주고받으면 DB와 서버 모두 거치지 않는다.

## 획득 대기 시간(acquire)
- 풀이 꽉 찼을 때 빈 연결을 기다리는 최대 시간. Sequelize 기본값은 **60초**.
- 길면 DB 장애 때 요청이 오래 매달리고, 헬스체크 대기가 쌓이고, 에러(와 에러 알림)가 늦게 난다.
- 줄이면(예: 10초) 빨리 실패해서 장애가 빨리 드러난다. 대신 부하가 몰릴 때 "기다리면 성공했을" 요청이 실패할 수 있다.

## Sequelize v6 기본값 (6.37.7 소스 확인)
`connection-manager.js`: `config.pool = _.defaults(config.pool || {}, { max: 5, min: 0, idle: 10000, acquire: 60000, evict: 1000 })`
→ `pool: { acquire: 10000 }`만 넣어도 나머지 기본값은 유지된다.

#flashcards
- Q: DB vCPU 2개일 때 풀 크기 경험식 값? → A: (2×2)+1 ≈ 5.
- Q: 연결 수가 max에 붙어 있는데 DB CPU도 높다면? → A: 풀을 늘려도 소용없음. 쿼리 개선이나 DB 사양 업.
- Q: Sequelize에서 pool.acquire만 설정하면 max는? → A: 기본값 5 유지(_.defaults 병합).
