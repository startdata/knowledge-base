# 이벤트 순서 보장 #stub

> [[Kinesis 파티션 키]] · [[Kafka 파티션과 컨슈머 그룹]] · [[Redis 분산락]] · [[멱등성]] 와 연결.

## 1. 보장되는 범위
- **파티션(샤드) 안**에서만 순서가 보장된다. 같은 키 → 같은 파티션 → 한 번에 한 컨슈머가 오프셋 순으로 처리
- **전역 순서는 없다.** 파티션이 2개 이상이면 파티션 간 순서 개념이 없다. 파티션 1개일 때 성립하는 전역 순서는 우연이고, 증설하는 순간 깨진다
- 배치 안에서 `Promise.all`로 병렬 처리하면 파티션 순서도 깨진다

## 2. 락과 큐의 차이 — 한 줄
**락은 "누가 들어가나"를 정하고, 큐는 "누가 먼저 들어가나"까지 정한다.**
- 분산락(SET NX)은 상호 배제만 준다. 대기 큐가 없어 락이 풀리는 순간 재시도 타이밍이 맞은 쪽이 잡는다 → 먼저 온 요청이 나중에 처리될 수 있다 → [[Redis 분산락]] §5
- 파티션은 큐라 들어온 순서로 쌓이고 한 컨슈머가 순서대로 뺀다
- 순서가 요구사항이면 락이 아니라 **키 기반 파티션 + 단일 컨슈머 직렬 처리**가 정석

## 3. 순서 무관(order-independent) 설계 — 순서에 의존하지 않는 편이 더 강하다
"순서를 지킨다"보다 "**순서가 바뀌거나 중복 도착해도 결과가 같다**"가 더 안전하고 확장에 유리하다.

| 동작 | 순서 필요? | 대신 쓰는 것 |
|---|---|---|
| 적재 (append-only 이력 등) | 아니오 | 이벤트 ID로 멱등 |
| 정렬·분석 | 아니오 | **발생 시각(occurredAt)** 컬럼으로 정렬. 저장 순서·ID 순서로 정렬하지 말 것 |
| "마지막 값만 유지" 상태 갱신 | **예** | 여기서만 파티션 순서에 의존. 또는 버전/시각 비교 조건부 갱신 |

순서 무관이면 배치 병렬 적재, 재처리, 리샤딩 후 순서 섞임, 컨슈머 병렬화에 모두 안전하다. 파티션 키의 순서 보장은 그 위의 보너스로 두고, 정확성은 멱등과 시각에 건다.

## 4. 시각 기준 정렬의 전제
- 발생 시각은 **이벤트를 만든 곳**(서비스)이 찍는다. 서버 간 시계 차이가 있지만 클라우드 인스턴스는 NTP 동기화로 ms 단위, 같은 대상의 연속 이벤트는 대개 한 서비스에서 나온다
- **저장 시각(createdAt)은 DB 기준으로 따로** 둔다. 비동기라 평시 수 초, 리플레이 시 수 시간 벌어진다. 분석은 발생 시각, 적재 감사는 저장 시각
- ID(UUID v7)의 시간 정렬은 ms 해상도까지라 tie-break로만 → [[UUID v7]]

## 복습 질문 #flashcards
- 메시징에서 순서가 보장되는 범위는? :: 같은 키의 파티션 안에서만. 전역 순서 없음.
- 분산락으로 순서를 보장할 수 없는 이유는? :: 상호 배제만 주고 대기 큐가 없어 먼저 온 요청이 나중에 잡을 수 있음.
- 순서 무관 설계의 두 축은? :: 이벤트 ID 멱등 + 발생 시각 정렬.
- 발생 시각과 저장 시각을 나누는 이유는? :: 비동기 지연·리플레이로 벌어지므로 분석은 발생 시각, 감사는 저장 시각.
