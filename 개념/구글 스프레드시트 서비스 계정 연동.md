# 구글 스프레드시트 서비스 계정 연동

#stub

서버 프로그램이 사람의 로그인 없이 구글 스프레드시트를 읽고 쓰는 방법. 사람 계정 대신
**서비스 계정**(프로그램용 구글 계정)을 만들어, 그 계정에게 시트 권한을 주고 API를 호출한다.

---

## 핵심 — 축이 두 개다

| 축 | 정하는 것 | 만들어지는 곳 | 실패 시 |
|---|---|---|---|
| **신원**(인증) | 호출자가 누구인지 | 서비스 계정 + 비공개 키 | 토큰 발급 실패 / 401 |
| **권한**(인가) | 그 신원이 이 파일에 무엇을 할 수 있는지 | 스프레드시트 공유 설정 | 403 |

**이 둘은 서로를 모른다.** 비공개 키 안에 파일 정보가 없고, 파일 공유 설정 안에 키 정보가 없다.
둘을 잇는 유일한 연결 고리는 **서비스 계정 이메일 문자열**이다.

```
비공개 키  ──서명──▶  "나는 bot@proj.iam.gserviceaccount.com 이다"
                                    │  같은 이메일이어야 성립
파일 공유  ──등록──▶  "bot@proj.iam.gserviceaccount.com 은 편집자"
```

여기서 실무 결론 두 개가 나온다.

- 키를 재발급해도 **이메일이 같으면 파일 공유는 그대로 유효**하다 → 키 로테이션이 싸다
- 서비스 계정 자체를 새로 만들면 이메일이 바뀌므로 **공유를 다시 해야** 한다

## 흔한 오해 — GCP IAM 역할은 파일 접근과 무관하다

서비스 계정에 프로젝트 소유자(Owner) 역할을 줘도 남의 스프레드시트는 못 건드린다.
드라이브 파일 권한은 **드라이브 ACL(공유 설정)** 이 결정하고, IAM은 GCP 리소스에만 적용된다.
그래서 이 용도로 서비스 계정을 만들 때 IAM 역할은 아무것도 주지 않아도 된다.

같은 이유로 **GCP 프로젝트 소유 계정과 시트 소유 계정이 같을 필요가 없다.** 서로 다른 조직이어도
공유 한 줄로 연결된다.

---

## 인증 흐름 (OAuth 2.0 JWT Bearer)

```
① 서버: 비공개 키로 JWT에 서명 (SHA256withRSA)
     클레임 = { iss: 서비스 계정 이메일, scope: 필요한 권한, aud: 토큰 엔드포인트, exp/iat }
② 서버 → https://oauth2.googleapis.com/token
     grant_type = urn:ietf:params:oauth:grant-type:jwt-bearer
③ 구글: 보관 중인 공개키로 서명 검증
④ 구글 → 서버: 액세스 토큰 (expires_in 기본 3600초 = 1시간)
⑤ 서버 → API: Authorization: Bearer <액세스 토큰>
```

**비공개 키는 네트워크로 나가지 않는다.** 서명을 만드는 데만 쓰이고, 구글은 자기가 가진 공개키로
검증한다. 그래서 개인키를 가진 쪽이 곧 그 계정 본인이며, 비밀번호처럼 "재설정"하는 개념이 없다 —
유출되면 그 키를 폐기하는 것 외에 방법이 없다.

대부분의 공식 클라이언트 라이브러리(`google-auth-library` 등)가 ①~④와 토큰 갱신을 대신 처리한다.
클라이언트 객체는 한 번만 만들어 재사용하면 요청마다 토큰을 새로 받지 않는다.

## 권한을 주는 두 가지 경로

| 방식 | 방법 | 쓰는 상황 |
|---|---|---|
| **파일 직접 공유** | 시트 공유창에 서비스 계정 이메일을 편집자로 추가 | 대상 파일이 정해져 있을 때. 설정이 가장 단순 |
| **도메인 전체 위임** | Workspace 관리자가 승인 + JWT `sub`에 가장할 사용자 이메일 지정 | 조직 구성원의 파일에 광범위하게 접근해야 할 때 |

직접 공유는 관리자 권한이 필요 없다. 반면 도메인 전체 위임은 사용자 동의 없이 데이터에 접근할 수
있어 공식 문서도 보안 주의를 강조한다.

**막히는 경우**: 파일이 Workspace 조직 드라이브에 있고 외부 공유가 차단돼 있으면,
`...iam.gserviceaccount.com`은 외부 도메인으로 취급돼 초대가 거부될 수 있다.
조직 정책으로 서비스 계정 **키 생성 자체가 금지**(`iam.disableServiceAccountKeyCreation`)돼 있기도 하다.

## 서버에 필요한 값

JSON 키 파일에서 두 개, 대상 파일에서 두 개.

| 값 | 출처 | 의미 |
|---|---|---|
| `client_email` | JSON 키의 필드 | 서비스 계정 식별자. **파일 공유에 등록한 문자열과 같아야 함** |
| `private_key` | JSON 키의 필드 | JWT 서명용 개인키 (비밀) |
| 스프레드시트 ID | URL의 `/d/` ~ `/edit` 사이 (44자) | 대상 파일 |
| 시트(탭) 이름 | 파일 하단 탭 | 대상 탭. 띄어쓰기까지 정확히 |

`client_email`의 `client`는 OAuth 용어로 "API를 호출하는 쪽"이라는 뜻이다. 메일함이 있는 주소가
아니라 계정 식별자이며, 서비스 계정을 만드는 순간 `<계정ID>@<프로젝트ID>.iam.gserviceaccount.com`
형태로 자동 발급된다.

## PEM 개인키를 환경변수로 넘기기

개인키는 원래 여러 줄 PEM인데 환경변수는 한 줄이다. 그래서 JSON에 저장된 `\n` **두 글자를
그대로 둔 채** 한 줄로 넣고, 코드에서 실제 개행으로 복원하는 방식이 흔하다.

```js
key: process.env.PRIVATE_KEY.replace(/\\n/g, '\n')
```

주입 경로에 따라 이미 개행으로 풀려 있을 수도 있다. 예를 들어 **YAML 큰따옴표 문자열은 `\n`을
실제 개행으로 해석**하므로(작은따옴표는 리터럴 유지), 이 경우 위 `replace`는 아무 일도 하지 않지만
값 자체가 정상 PEM이라 그대로 동작한다. 양쪽 다 통과하는 게 이 코드의 장점이다.

깨지는 패턴: 큰따옴표 없이 넣어 값이 잘리는 경우, `-----BEGIN/END-----` 헤더를 빼먹는 경우.

## 에러 코드로 원인 좁히기

연동에서 이 표 하나로 대부분의 디버깅이 끝난다.

| 증상 | 잘못된 축 | 원인 |
|---|---|---|
| 토큰 발급 실패 / 401 | 신원 | 개인키 형식 깨짐, 폐기된 키, 이메일 불일치 |
| 403 | 권한 | 파일에 서비스 계정이 공유되지 않음 / 뷰어 권한 |
| 404 | 대상 | 파일 ID 오타 |
| 400 | 대상 | 탭 이름 불일치, 잘못된 범위 표기 |

## 쓰기 API에서 함께 챙길 것

- `values.append`는 **마지막 데이터 행 다음에** 행을 추가한다. 범위는 `탭이름!A:L` 형태
- `valueInputOption`: `RAW`는 문자열 그대로, `USER_ENTERED`는 UI 입력처럼 파싱(날짜·숫자 변환).
  요청 단위 설정이라 컬럼마다 다르게 줄 수 없다
- `USER_ENTERED`를 쓰면 `=` `+` `-` `@`로 시작하는 사용자 입력값이 **수식으로 해석**된다.
  앞에 작은따옴표를 붙여 이스케이프한다 (수식 인젝션 방지)
- 5xx·429만 재시도하고 4xx는 즉시 실패시키는 게 맞다 — 권한·ID 오류는 재시도해도 결과가 같다
  → [[재시도 전략]]
- 재시도로 중복 행이 생길 수 있으므로, 쓰기 전에 같은 행이 있는지 확인하는 식의 방어가 필요하다
  → [[멱등성]]

## #flashcards

- 서비스 계정에 GCP 프로젝트 소유자 역할을 주면 남의 스프레드시트를 수정할 수 있나?
  → 아니다. 드라이브 파일 권한은 IAM이 아니라 공유 설정(ACL)이 결정한다
- 개인키를 재발급하면 시트 공유를 다시 해야 하나?
  → 아니다. 이메일이 같으면 공유는 유효하다. 계정을 새로 만들면 다시 해야 한다
- 403과 토큰 발급 실패는 각각 어느 축의 문제인가?
  → 403은 권한(공유), 토큰 발급 실패는 신원(키)
- 비공개 키는 구글로 전송되나?
  → 아니다. 서명 생성에만 쓰이고, 구글은 보관 중인 공개키로 검증한다
