# 멱등성 (Idempotency)

## 한 줄
같은 연산을 여러 번 수행해도 결과가 한 번 한 것과 같음. 배치는 재실행이 일상이라 **필수**.

## 왜 배치에 필수인가
장애 재시작·중복 트리거·수동 재실행이 일상. 멱등하지 않으면 재실행이 데이터를 오염시킨다.

## 구현: 검사 vs 키 설계
- **검사(read-then-write)**: `find` 후 없으면 `save`.
  - 약점 ① 조회와 저장 사이 경쟁 조건(다른 쓰기 끼어듦) ② 중복 판정 로직이 늘수록 버그 표면 증가.
- **키 설계(권장)**: **자연키**를 저장 키로 → 같은 데이터는 같은 자리에 덮어쓰기.
  - 멱등성이 *로직*이 아니라 *구조*에서 나온다.
  - 예: `transactionId`(UUID)를 키로 upsert → 몇 번 저장해도 결과 동일.

## upsert
insert-or-update를 원자적으로. RDB는 `ON CONFLICT` / `MERGE`, file DB(node-json-db)는 키 경로 덮어쓰기(`push(path, data, false)`).

## 자연키 vs 대리키
- **자연키(비즈니스 키)**: 데이터 자체의 고유 식별자(transactionId). **중복 판정 기준은 항상 자연키.**
- 대리키(surrogate): auto-increment 등 시스템 생성. 중복 판정엔 부적합.

## 수집 방식과 독립
[[증분 수집]]을 해도 멱등은 필요하다 — 제공 측이 중복을 줄 수도, 배치가 재실행될 수도 있으니. **멱등성은 수집 방식과 무관한 기본 안전성.**

## 메시지 소비자의 멱등 (at-least-once 전달) — 2026-09 추가
Kinesis·Kafka·SQS는 at-least-once. 체크포인트 전에 컨슈머가 죽으면 같은 레코드를 다시 받고, 릴레이가 재발송하면 같은 이벤트가 또 온다. 소비자가 중복을 흡수해야 한다.

**구조로 만드는 법:** 이벤트 ID를 **생성 시점에 한 번** 발급해([[UUID v7]], [[Outbox 패턴]] §3) 저장 대상의 **PK**로 두고, 충돌 시 아무것도 바꾸지 않는 upsert.
```sql
INSERT INTO user_action_history (id, ...) VALUES (?, ...)
ON DUPLICATE KEY UPDATE id = id;   -- no-op. 유니크 충돌만 무시, 다른 에러는 그대로
```
- `INSERT IGNORE`는 쓰지 말 것: 유니크 위반뿐 아니라 데이터 잘림·타입 오류도 함께 삼킨다
- no-op를 실제 갱신으로 바꾸지 말 것: 적재 후 어드민이 바꾼 컬럼(고정 플래그 등)을 재전달 레코드가 덮어쓴다. 같은 ID의 레코드는 내용이 같으니 갱신할 게 없다
- **멱등해지는 것은 "저장"뿐이다.** 컨슈머가 저장 외에 알림 발송 같은 부수효과를 하면 그건 별도로 막아야 한다 → 아래 Inbox

## idempotency key 패턴이란
"같은 요청을 두 번 보내도 한 번만 실행된다"를 **요청마다 붙이는 고유 키**로 구현하는 패턴. 결제 API(Stripe 등)가 대표적이고 IETF에 `Idempotency-Key` 헤더 표준 초안이 있다.

**왜 쓰나.** 네트워크는 응답을 잃어버린다. 클라이언트가 결제 요청을 보냈는데 응답이 안 오면 성공했는지 알 수 없어 재시도하는데, 재시도가 새 요청으로 처리되면 **이중 결제**가 된다. 재시도는 [[재시도 전략]]의 전제인 "요청이 멱등인가"를 만족해야 하고, 원래 비멱등인 요청(생성·결제)을 멱등하게 만드는 장치가 이 키다.

**동작.**
1. 클라이언트가 논리적 작업 하나당 고유 키(UUID)를 만들어 헤더에 실어 보낸다
2. 서버는 키 테이블에 `키 → 처리 결과(응답)`를 저장한다. 동시 요청 대비로 **처리 전에 키를 먼저 insert(claim)** 해 둘 중 하나만 실행되게 한다
3. 같은 키가 다시 오면 실행하지 않고 **저장된 응답을 그대로 돌려준다**
4. 키는 보통 24시간쯤 지나 만료

**이벤트 파이프라인의 이벤트 ID와의 관계 — 같은 개념, 다른 위치.**

| | API idempotency key | 이벤트 ID (파이프라인) |
|---|---|---|
| 키 생성 | 클라이언트, 요청마다 | 발행 측, 기록 시점에 |
| 키 전달 | HTTP 헤더 | payload 안 |
| 키 저장 | 별도 키 테이블 | 저장 대상 row의 PK 자체 |
| 중복 시 | 저장된 응답 반환 | upsert no-op |
| 만료 | 있음 | 없음(데이터로 남음) |

처리가 "row 하나 insert"면 대상 테이블의 PK가 키 테이블을 겸하므로 더 단순하다.

**Inbox 패턴 (별도 키 테이블이 필요해지는 경우).** 컨슈머가 저장 외에 **부수효과를 여러 개** 하면 PK 충돌은 저장만 막고 알림 중복은 못 막는다. 그때는 `processed_events(event_id PK)` 테이블을 두고 **부수효과와 같은 트랜잭션에서 먼저 insert**해 이미 처리한 이벤트인지 판정한다. [[Outbox 패턴]]의 소비 측 대응물.

#flashcards
- Q: read-then-write가 멱등 보장에 약한 이유? → A: 조회-저장 사이 경쟁 조건 + 검사 로직의 버그 표면.
- Q: 멱등성을 "구조"로 만드는 방법? → A: 자연키를 저장 키로 한 upsert.
- Q: 증분 수집을 하면 멱등성이 불필요한가? → A: 아니다. 제공측 중복·재실행 때문에 여전히 필수.
- Q: at-least-once 소비자에서 중복을 구조로 막는 법? → A: 생성 시점에 발급한 이벤트 ID를 PK로 두고 no-op upsert.
- Q: INSERT IGNORE 대신 ON DUPLICATE KEY UPDATE id=id를 쓰는 이유? → A: IGNORE는 유니크 위반 외 다른 에러도 삼킨다.
- Q: idempotency key 패턴은 왜 쓰나? → A: 응답 유실로 재시도할 때 비멱등 요청(결제·생성)이 두 번 실행되는 걸 막으려고. 키로 같은 요청을 식별해 저장된 응답을 돌려준다.
- Q: 이벤트 ID PK 방식과 idempotency key 테이블 방식의 차이? → A: 같은 개념. 키를 대상 row PK에 두느냐 별도 테이블에 두느냐, 중복 시 no-op이냐 응답 반환이냐.
- Q: 부수효과가 여럿인 컨슈머는 왜 별도 processed 테이블이 필요한가? → A: PK 충돌은 저장만 막고 알림 등 부수효과 중복은 못 막으므로 같은 트랜잭션에서 먼저 claim해야 한다(Inbox).
