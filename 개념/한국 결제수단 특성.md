# 한국 결제수단 특성 — 해외 모델에 없는 것 #stub

> [[결제 상태 기계]] · [[구독 청구 도메인 모델]] · [[웹훅 처리 패턴]] 와 연결.
> 세션: [[세션/leaf-결제개편/설계결정-서사]]

## 1. 빌링키 카드 정기결제
- 카드 정보를 PG에 등록하고 빌링키(토스 `billingKey`, 포트원 v1 `customer_uid`)만 보관. 카드 번호는 우리 DB에 없다(PCI 범위 밖).
- **토스페이먼츠는 자체 스케줄링을 제공하지 않는다** → 가맹점이 청구 시점에 승인 API를 직접 호출. 포트원 v1은 PG 측 예약 API가 있으나, 그러면 멱등성·조회·재시도를 우리가 통제하지 못한다.
- 승인과 매입 요청이 한 번의 호출로 끝남 → 선점(authorize) 상태 없음. 해외 PG와 다른 점.
- 실패 원인(만료·한도·정지)은 동기 응답으로 즉시 안다.
- **PG를 바꾸면 빌링키는 이관되지 않는다** → 전 고객 카드 재등록.

## 2. CMS 자동이체 (효성·나이스·금융결제원)
- 출금 동의(서면·전자) → 중계기관에 계좌 등록 → 지정일(휴일이면 익영업일)에 **일괄 출금**.
- **출금 결과는 출금일 당일~익일, 이용기관 입금은 D+1(신규 기관 D+3)**. 결제 확정 기준은 출금 결과, 입금은 정산 대사 대상. 둘을 혼동하면 이용권 개방 시점과 대사 모델이 어긋난다.
- 요청이 건별 API가 아니라 파일/배치. 멱등키는 `(계좌, 출금일, 청구서)`. 결과 수신은 웹훅과 같은 inbox 구조에 소스만 다름.
- 사전 안내(출금 2~3일 전) 의무 → 청구서를 리드타임만큼 앞서 발행.
- 수수료가 차감형인지 월 후청구형인지 기관마다 다를 수 있음(확인 필요).
- 취소 = PG 취소가 아니라 우리 계좌 → 고객 계좌 환불 이체.

## 3. 가상계좌·무통장
- PG가 계좌 발급, 고객 입금 시 웹훅. **만료 시 웹훅이 오지 않음** → 만료 추적은 자체 배치.
- 과입금·부족입금·만료 후 입금(반환) 처리 필요.
- 고객이 입금하려면 금액·계좌가 먼저 있어야 함 → 청구서가 결제보다 앞선다(D−7 등).

## 4. 증빙
- 카드: 신용카드매출전표. 매출전표 발급 거래에 세금계산서 중복 발급 금지 원칙 — 그러나 B2B 카드 고객이 세금계산서를 요구하는 경우가 흔함(세무 확인).
- CMS·이체: 현금성 → 세금계산서(사업자) 또는 현금영수증(소비자·사업자 지출증빙). 동시 발행 금지.
- 발행 시점은 결제 확정이 아니라 **부가세법 공급시기** 기준(계속적 공급은 대가의 각 부분을 받기로 한 때, 선수금은 선발행 가능). 미납 건 발행 의무 여부 세무 확인.
- 증빙 종류는 결제수단의 고정 속성이 아니라 고객(사업자 여부)·수단·선택의 조합.

## 5. "자동이체"라는 말의 다의성
CMS 자동이체 / 금융결제원 직접 연동 / 오픈뱅킹 출금이체 / 실시간 계좌이체(PG 결제창)가 모두 "자동이체·이체"로 불린다. 어댑터와 상태 경로가 다르므로 요구사항에서 어느 것인지 먼저 확인.
